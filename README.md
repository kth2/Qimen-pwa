# 奇门遁甲 · 排盘占断 PWA

浏览器内运行的奇门遁甲排盘 + AI 占断渐进式 Web 应用（PWA）。纯前端、离线可用，
GitHub Pages 静态托管。支持 **时家奇门**（转盘 / 飞盘）与 **山向奇门 / 宅盘**。

## 山向奇门 / 宅盘

### 是什么

时家奇门以「时间」（节气 + 时辰）起局；**山向奇门**以「空间」（房宅的**坐山**朝向）
起局，用于阳宅风水的方位吉凶分析。本应用新增此模式，与时家完全并存、互不影响。

### 本实现所采用的方法（method = `standard`）

山向 / 宅盘奇门流派众多、起局法不一。本实现选取**可查证且与本引擎自洽**的一种，
作为默认 `standard` 法，步骤如下：

1. **二十四山定盘**：罗盘顺时针，子 = 正北 = 0°，每山 15°。
2. **坐山 → 节气**：采用通行的「罗盘节气」对应——子 = 冬至（正北）、午 = 夏至（正南）、
   卯 = 春分（正东）、酉 = 秋分（正西），其余顺布（见 `core/shanxiang.js` 的
   `MOUNTAINS` 表）。由此把坐山映射到某一节气。
3. **三元 → 局数**：节气 + 上/中/下元决定局数。三元由坐山在本山 15° 内的 5° 分段确定
   （只给山名不给度数时默认取**中元**）。阴阳遁随节气自动落定（冬至→芒种为阳遁、
   夏至→大雪为阴遁）。
4. **局数取值**：`core/shanxiang.js` 的 `JU_TABLE` 由本引擎 `calculateJuShu` **全量采集**
   而来（与《二十四节气定局歌》一致，如冬至 上1/中7/下4、夏至 上9/中3/下6）。
   因此山向所定之局与时家**同源**，可对拍验证——见测试
   「24 山坐局全量与引擎一致」。

> **为何这样选**：如此定局不引入任何杜撰的局数表，而是复用引擎已验证的三元定局，
> 只是把「键」从时间换成空间（坐山）。这是本仓库能给出的最可查证、最自洽的实现。

### 时间激活层（混合盘）

坐山只定「局 / 地盘」这一**固定宅基**；**值符 / 值使 / 天盘 / 暗干**属动态层，需一个
「何时」来激活。故采用**空间定局 + 时间起符**的混合盘：

- 传入 `date` → 以该时刻起符（推荐）；
- 传入 `year`（入住 / 动土年）而无 `date` → 以该年立春 12:00 近似作激活时刻；
- 都不传 → 默认当下。

### 方位对齐

九宫沿用本应用时家盘一致的**上南下北**罗盘朝向（离九在上=正南、坎一在下=正北、
震三在左=正东、兑七在右=正西），各宫 `direction` 字段标注方位，可直接叠加到采用
同一「坐北朝南 / 二十四山」朝向的户型平面图上。向首宫为纳气之口，坐山宫为宅主根基，
中五为宅心。

### 局限与诚实声明

- 山向 / 宅盘奇门**并无单一公认起局法**；亦有流派以 315°–134° 定阴阳遁、或以向首、
  或以六甲宅盘专法起局，所得盘不同。本实现取上述一种可查证方案作默认，`method`
  参数已预留以便日后接入其它流派（当前仅实现 `standard`，传入其它值会明确报错而非
  静默出错盘）。
- 时间激活层（值符值使随日期）是本实现的工程化选择；不同宅盘体系对「宅盘是否需要 /
  如何引入时间」看法不一。

### 公共 API


## 旺衰与四害（提升实战准确度的关键补全）

### 为什么需要

排盘引擎输出九宫元素、格局与吉凶，但**不计算旺相休囚死、入墓、击刑**。而两派纲要通篇
依赖旺衰——「旺相逢生为得」「得令为旺，失令/入墓/空亡则力弱」「旺相足数、休囚减半」。
数据缺位时，AI 只能凭感觉猜强弱：**吉凶方向对了，力量判断却错**，这是实战断事
「越来越不准」的首要原因。`core/wangshuai.js` 补齐这一层。

### 补算内容

1. **旺相休囚死**（以月支定四时）：当令者旺、令生者相、生令者休、克令者囚、令克者死。
   对每宫的 宫/九星/八门/天盘干/地盘干 分别定状态。

   | 当令 | 旺 | 相 | 休 | 囚 | 死 |
   |---|---|---|---|---|---|
   | 春(寅卯·木) | 木 | 火 | 水 | 金 | 土 |
   | 夏(巳午·火) | 火 | 土 | 木 | 水 | 金 |
   | 秋(申酉·金) | 金 | 水 | 土 | 火 | 木 |
   | 冬(亥子·水) | 水 | 木 | 金 | 土 | 火 |
   | 四季(辰未戌丑·土) | 土 | 金 | 火 | 木 | 水 |

2. **十干入墓**（通行口诀，自洽覆盖十干）：**乙丙戊→乾六、甲癸→坤二、丁庚己→艮八、壬辛→巽四**。
3. **六仪击刑**（仪所代地支刑其所落宫之支）：戊→震三、己→坤二、庚→艮八、辛→离九、壬→巽四、癸→巽四。
4. **奇门四害汇总**（门迫/击刑/空亡/入墓）与**能量估计**：以天盘干旺衰为基，门迫·击刑·空亡各减半、
   入墓仅余两成，多害**相乘**递减，得每宫约略力量值。

### 效果示例

某盘 4 宫，引擎仅判「小凶」；补算后为 `天盘壬入墓 + 天盘壬击刑`，力量约 **0.02**——
实为几近无力之宫。此类差异正是断错成败的关键所在。

### 纲要同步

三份 `assets/*-method.md` 均已新增「旺衰与四害」节（判法、减力、要诀），并在解读流程中
加入 **3.5 称量力量（必做）**：*吉凶定方向，旺衰定成败大小与迟速，二者须合参*。
同时补全了原先指向不存在文件的 **81 干加干格局**速查表（原为死链）。

### API

```js

WS.analyze(pan);                              // → { season, gongs: {1..9: {旺衰/四害/力量}} }
```

## 应期与数字（修复"填实之日"答错的根因）

### 症结：盘面与提示词没接好

引擎**算出了空亡地支**（`kongWangZhi`，如 `["戌","亥"]`），但序列化给 AI 的盘面只写：

```
【空亡宫】6、6        ← 只有宫号，而且重复
```

**从头到尾没告诉 AI 哪两个地支空亡**。纲要虽写"空亡则填实冲实"，AI 无从知道填哪个支，
只能臆造——实测出现「午未空亡 → 应在**戊己日**或**辰巳日**」这类错误：戊己是**天干**、
辰巳是**无关地支**，皆非午未之填实或冲实。正确应为 填实＝**午日、未日**，
冲实＝**子日**(冲午)、**丑日**(冲未)。

### 补算内容（`core/yingqi.js`）

| 项 | 算法 | 输出 |
|---|---|---|
| **空亡填实/冲实** | 取 `kongWangZhi`（并对重复宫号去重） | 空亡支本身之日 / 其六冲支之日 |
| **驿马** | 取 `maStar.zhi` | 寅申巳亥 之日/月 |
| **入墓冲墓** | 入墓宫 → 墓库支 → 六冲 | 冲墓之日 |
| **用神宫定日** | 用神落宫之天/地盘干 | 干日（如天盘丙→丙日） |
| **河图数** | 甲乙3·8 丙丁7·2 戊己5·10 庚辛9·4 壬癸1·6 | 各宫数字候选（另有宫数一路，见「取数」Phase 21） |

**地支六冲**：子午、丑未、寅申、卯酉、辰戌、巳亥。

文本块以「**已据本盘算出具体干支，必须照用，禁止自行臆造**」开头，并明写
「不得改用天干（如戊己日）或其它地支充数」。三份纲要的应期节亦同步加入此禁令与正例。

### 测试

```bash
node core/yingqi.test.js
```

含**用户实测错误场景的回归**：午未空亡必得 午日/未日 与 子日/丑日，
且取值行中不得出现天干日或无关地支日；另覆盖六冲互逆完整、河图数、空亡宫去重、
无空亡时不编造、真实盘与引擎数据一致、跨多盘应期恒为合法地支日。

## 结构化推理层（Structured Reasoning Layer）

### 为什么加这一层

原先送进 AI 的是一大段自然语言盘面文本，模型难以分辨其中**哪些是引擎算出来的事实、
哪些是应用给的规则、哪些是传统象义**，于是常把三者混为一谈，甚至自行补一套用神与象义。
本层不改动排盘与既有分析，只在其上把喂给模型的内容重新组织为可核验的结构：

```
用户问题 → 占类(domain) → 用神(YongShen) → 既有盘面/分析
                                              ↓
                                     象义判读(XiangYi)      ← Phase 2
                                              ↓
                                      证据包(Evidence) → 既有 LLM 层
```

分工如下：

1. **排盘计算** —— `engine.bundle.js`（未改动）
2. **确定性分析** —— 引擎 `jiuGongAnalysis`/`geju` + `core/wangshuai.js` + `core/yingqi.js` + `core/shanxiang.js`（均未改动）
3. **符号知识** —— `knowledge/symbols.json`（与占类无关的通用象义）
4. **占类用神** —— `knowledge/domains.json` + `core/yongshen.js`
5. **占类象义** —— `knowledge/domain-rules.json` + `core/xiangyi.js`（见「占类象义推理层」）
6. **应期时间线** —— `knowledge/timing-rules.json` + `core/timing.js`（见「应期时间线」）
7. **取数** —— `knowledge/qushu-rules.json` + `core/qushu.js`（见「取数」，Phase 21）
8. **LLM 解读** —— `llm.js`（未改动）

模型收到的不再只是原始盘面文本，而是一份**结构化证据包**。

### 三类证据

| 类型 | 含义 | 对模型的约束 |
|---|---|---|
| `FACT` | 引擎算得的盘面事实（用神落宫、空亡、驿马、四柱、局） | 不得改写、不得虚构 |
| `RULE` | 应用内确定性分析（引擎吉凶/格局、旺衰四害、应期数字） | 优先于模型自身判断 |
| `SYMBOL` | 取自 `symbols.json` 的传统象义，**与占类无关的原料** | 优先采用，可组合，不可替换为自创象义 |
| `READING` | 取自 `domain-rules.json` 的**占类象义判读**（Phase 2） | 涉及其所断元素时优先采用其读法；`[助]/[阻]` 只表倾向，非成败断语 |
| `TIMING` | 取自 `core/timing.js` 的**应期锚点**（Phase 4） | 断应期只在其列出的候选中选，不得自造日辰；`[★强]` 表机制与用神的关系，非应验概率 |
| `CALIBRATION` | 取自**本机案例记录**的经验统计（Phase 5） | 这不是纲要；只供权衡着墨详略，**不得据此推翻 READING**；样本量随条呈现 |

「证据优先」而非「只许用证据」：模型仍可组合象义、推演情境、说明关系、表达不确定；
但不得另立用神体系、不得虚构盘面元素、不得推翻确定性计算。

### `knowledge/symbols.json`

结构化象义库（v1.0.0），分七类：`wuxing` / `bagua` / `jiugong` / `tiangan` / `jiuxing` / `bamen` / `bashen`。
每条统一 schema：

```json
{ "name": "...", "wuxing": "...",
  "core": [], "people": [], "events": [], "objects": [],
  "places": [], "body": [], "psychology": [], "industries": [], "keywords": [] }
```

**这是初版，刻意保守**：只收录两派纲要与通行奇门典籍共有、无争议的基础衍象，宁缺勿造；
不适用的栏位留空数组，不代表「无此象」。`industries` / `psychology` 两栏属现代引申而非古籍原文。

感情占类**未**引入性别硬编码取用；`乙` 为引擎既有规则所取，此处保留以免与引擎判定冲突。

## 用神来源归属与优先级（Phase 1.1）

### 三个不同的概念，不得合并

审计发现最初的实现把三者揉进了同一个 `roles` 字段，导致「这个用神是谁定的」无法回答。
现已严格分列：

| 概念 | 字段 | 回答的问题 | 谁产生 |
|---|---|---|---|
| 引擎用神 | `engineRule` | **本盘**实际算出的用神是什么？ | `engine.bundle.js` |
| 占类用神 | `domainRule` | 这**类**问题应该看什么？ | `knowledge/domains.json` |
| 查看清单 | `examine` | 本次最终看哪些元素？ | 二者归并，逐条带 `origin` |
| 裁定 | `resolution` | 谁说了算、为什么、排除了什么？ | `core/yongshen.js` |

`examine` 中每一条都带 `origin: 'engine' | 'domain' | 'both'`，证据包与提示词均按此标注。

### 优先级规则（确定性）

```
引擎用神（针对本盘，权威）
      ↓  引擎未匹配到特定占类时才轮到
占类用神（通用查看范围，仅作补充）
      ↓
证据包（分列呈现，标明裁定）
      ↓
LLM（按标注取舍，不得自行另取）
```

- 引擎 `matched === true` → `resolution.authority = 'engine'`。占类映射降为补充视角，**不覆盖**引擎判定。
- 引擎 `matched === false`（综合类）→ `resolution.authority = 'domain'`。
- 两者的差异记入 `resolution.conflicts`（`domain-extra` / `engine-extra`），留痕供人工校订，**不自动取舍**。

### 零串味：盘别隔离

`knowledge/domains.json` 的取用**全部源自转盘传统**，文件顶部以 `appliesTo: ["zhuanpan"]` 显式声明。
`core/yongshen.js` 依盘面 schema 自动判定盘别（飞盘有 `renPanMen`/`tianPanYi`），
遇飞盘时把 domains.json 的专属取用整体排除，只保留：

1. 引擎自己算出的用神（飞盘走 `feipanPredict.YONG_SHEN_RULES`）
2. `schoolNeutral` 声明的结构性元素（`值符` / `值使` / `时干`）

排除项记入 `resolution.excluded` 留痕，提示词中只报数量不报名单（避免反向提示模型）。
**`日干` 不属于 schoolNeutral**——「日干为人」是转盘断法，飞盘以年命/时干宫为主宰。
山向盘复用转盘引擎机器，按 `zhuanpan` 处理。

### 界面「目的」→ 引擎占类

界面下拉框的取值与引擎内部占类名并不同名。引擎 `classifyQuestion` 的 `fallbackCategory`
参数要求传**引擎占类名**，直传界面值会静默回落「综合」并丢掉该占类的专用用神：

| 界面目的 | 引擎占类 |
|---|---|
| 财运 | 求财 |
| 健康 | 疾病 |
| 学业 | 功名 |

其余 12 项同名。此映射表现存于 `domains.json` 的 `uiPurposeToEngineCategory`，
经 `YongShen.toEngineCategory()` 使用。**这是 Phase 1.1 修复的一个既存缺陷**：
修复前，当问句不含关键词时，选择「财运/健康/学业」会丢失对应的专用用神。

### 象义溯源

每条 SYMBOL 条目记录 `source: "knowledge/symbols.json"`、`category`、`element`，
以及 `fields`——真正贡献了词条的知识库栏位（截断后落空的栏位不会被声明，否则溯源会说谎）。

### 学派纲要仍然独立送达

`assets/*-method.md` 由引擎 `buildPrompt()` 放入 **system prompt**，结构化证据包放入 **user message**。
二者互补而非替代，最终送达模型的是：

```
system : 学派纲要(method.md) + AI_DISCIPLINE + EVIDENCE_DISCIPLINE
user   : 引擎盘面文本 + 日干/时干落宫 + 结构化证据包 + 山向背景
```

飞盘专属的三乙四宫（天乙/太乙/地乙/时干宫/年命宫）由引擎 `buildPrompt` 直接写入 user message，
证据包**不重复承载**，避免同一内容两次入提示词。

## 占类象义推理层（Phase 2 · Domain Intelligence）

### 症结：Phase 1 交付的是原料，不是读法

Phase 1 解决了「怎么把结构化证据喂给模型」，但 `symbols.json` 里的象义是**与占类无关**的：
无论问财、问病、问官司，「生门」都只是那一句「生发 / 财利 / 生机」。于是模型拿到的仍是原料，
**「在这个具体问题里它意味着什么」全靠自由发挥**——同一张盘换个问法，解读就漂。

本层补上这一步：

```
Phase 1：怎么把证据喂给模型          → FACT / RULE / SYMBOL
Phase 2：在这个问题里该怎么读这些证据 → READING
```

### 为什么必须按占类来读

同一个「旺」，角色不同则结论相反：

| 元素 | 角色 | 旺相 | 空亡 / 入墓 |
|---|---|---|---|
| 生门 | 财源 | **助**：财源有力、进财可期 | **阻**：财看得见难兑现 / 财被困住 |
| 庚 | 竞争、阻力 | **阻**：竞争者强势、同行分利 | **助**：阻力落空、对手受困 |

脱离占类角色谈旺衰是没有意义的。`domain-rules.json` 中这两条规则的触发条件（`when.state`）
**逐字相同**，差别只在角色——单测 `生门旺相判为助、庚旺相判为阻` 就钉住这一点。

### 三类判读

| scope | 是什么 | 例 |
|---|---|---|
| `condition` | 单象 × 旺衰/四害 | 生门 + 空亡 → 财看得见而难兑现，须待填实/冲实 |
| `combination` | 两象**同宫**相遇（其义不等于两象相加） | 生门 + 玄武 → 暗财、账目不明、防欺诈 |
| `relation` | 宫际五行生克（定成败向背） | 我方宫 生 财源宫 → 先投入后见利、脱泄耗力 |

组合**只跑规则表列出的对**，不做全排列——组合数必须由占类相关性约束，否则爆炸。
这也是 Phase 3（三象组合）的地基：扩展点在规则库，不在代码。

### 角色权重（Phase 2.2）

求财登记的角色与权重：

| 元素 | 角色(aspect) | 权重 |
|---|---|---|
| 生门 | 财源 | ★★★★★ |
| 日干 | 我方 | ★★★★★ |
| 戊 | 资金 | ★★★★ |
| 开门 / 六合 / 庚 / 时干 | 机会 / 合作 / 竞争 / 事体 | ★★★ |
| 值符 | 贵人 | ★★ |

权重有两个作用：① 证据包按它给 `SYMBOL` 排序，**截断时先保重点**；
② 写进提示词，告诉模型「★★★★★ 者逐条展开，★★ 者点到为止，不要平均用力」。

### 边界（与 Phase 1 一脉相承）

- **不下吉凶断语**。`polarity` 只表示该条判读对本占类是助力 / 阻力，成败仍归引擎与模型综合。
  倾向计数明标「非结论」，防止被当成打分。
- **只读不写**。条件只读盘面与 `wangshuai` 已算出的旺衰四害，绝不反过来改写 `FACT`；
  干的入墓/击刑只在该干**确实摆在天地盘上**时才断（日干为甲经值符定位者不硬断），
  与 `wangshuai` 严格同源，杜绝「象义层说入墓、旺衰块说没有」。
- **宁缺勿造**。八神不参五行，故对八神写 `state` 条件永不命中——宁可漏判也不放宽匹配。
  每条 `concept` 都须能追溯到 `basis` 所引《解断方法纲要》条文。
- **零串味**。规则库源自转盘传统（`appliesTo: ["zhuanpan"]`），遇飞盘盘面**整体停用**
  并说明原因，不降级套用；提示块此时不会漏出任何转盘取用。
- **规则未建 ≠ 盘上无碍**。占类未建成时在库中标 `status: "pending"`，明确告知模型
  「这是应用尚未收录该占类规则，不等于盘上没有阻碍」。六大占类已于 Phase 2.3 全部建成，
  该机制以合成规则库继续受测（日后新增占类必先经此态）。

### 缺件降级

| 缺什么 | 后果 |
|---|---|
| `domain-rules.json` 加载失败 | 证据包不含 `READING`，其余照旧 |
| 未传 `wangshuai` | 旺衰类与宫际关系规则停用，空亡/驿马类仍可用；`degraded: true` 并留痕 |
| 占类 `pending` / 盘为飞盘 | 整体停用并说明原因 |

任何一种都不阻断解读流程。

### API

```js
XiangYi.load(domainRulesJson);
XiangYi.analyze({ domain, chart, wangshuai, options: { school } });
// → { applicable, status, reason, focus, readings, combinations, relations, absent, tally, degraded, notes }
XiangYi.toPromptBlock(result);
```

确定性、无副作用：同盘同占类必得同一结果，输出按「权重降序、同权按 id 字典序」稳定排序。

### 常量漂移守卫

`core/` 各模块各自留存一份五行生克 / 入墓击刑 / 九宫方位常量副本（为保持可独立移植）。
`xiangyi.test.js` 逐项比对 `wangshuai` 与 `yongshen` 的副本，并交叉验证元素落宫与
`YongShen.locate` 一致——任一处改动而另一处未跟进，测试即失败。

### 两处 DSL 扩充（皆源自纲要，非新造断法）

- **`when.gongState`（宫旺衰）**：八神不参五行，`wangshuai` 亦不产 `shenState`，故六合/值符/玄武
  的力量只能以**所落之宫**论——这正是纲要·四之二所列「用神/值符/值使/日干/时干**宫**旺相→
  事有力、可成、应速」的口径。对八神写 `state` 仍永不命中，且有单测禁止规则库这样写。
- **`map.chong`（对宫相冲）**：九宫各有所属地支（坎一子、坤二未申…），对宫之支恰为六冲，
  故「二宫相冲」即对宫关系。用于承载纲要·二节婚姻行「六合旺吉、**被冲克则散**」与
  一节「逢冲主散、速决、动」。相冲与生克并不互斥（坤二与艮八既比和又相冲），
  故 chong 另行加判、不覆盖生克那一条，且仅在规则显式声明 `map.chong` 时才产出。

### 各占类的边界处理

- **感情**：乙(妻)/庚(夫) 为纲要原文，本层如实呈现其传统象义，但 `roleType` 为 `party`——
  二者的旺衰**只报力量强弱、polarity 恒为 0**，不预设吉凶，更不据此推断求测者的性别或关系形态；
  那须由用户所述情境决定，交由模型结合问句处理。
- **健康**：`safetyNote` 随占类走，在 `XiangYi` 与 `Evidence` 两处提示块中**紧贴判读**呈现
  （不只依赖提示词末尾的通用纪律），且**本层因盘别隔离而停用时照样送达**。判读用词有单测
  扫描，禁止出现确诊式断言。任何把宫位/八卦身体类象映射为具体脏器病变的规则一律未收。
- **官司**：不写「克庚＝必胜」——纲要原文为「开门生我**克彼**则胜」，是三项并举的条件；
  规则层只提供优劣势证据，胜败断语由模型综合。单测扫描禁止胜败措辞。
- **失物**：**不为失物本身立固定符号**——纲要作「类象定物，方位定处」，物之类象须由玄武
  所落之宫的门/星/神/天地盘干在 SYMBOL 层现取。方位判读逐条引纲要·三节《方位（九宫定方所）》
  表的对应行；`relations` 刻意留空（纲要失物行未以生克断失物）。

### 刻意未收的规则

每个占类的 `_omittedNote` 字段逐条记录了「本可以写、但纲要不支持故未写」的规则及其理由，
例如：事业不借用功名行的天辅、不给庚单立竞争强弱条件；官司不硬派「天盘为客、地盘为主」的
原被告角色（引擎未产出可靠标识）。**留白本身也是可审计的**。

## 应期时间线（Phase 4 · Timing）

### 症结：干支算准了，但是一张平铺的表

`core/yingqi.js` 已经把应期所需的具体干支全部算准（填实/冲实/冲墓/马星/宫干日辰/河图数），
Phase 之前的错误——「午未空亡 → 应在戊己日」——也早已修掉。但它输出的是一张**平铺的表**：
九宫的干日全列、空亡与冲墓并陈。**谁要紧、谁先到、为什么是这个日子，仍要模型自己从表里挑**。
实测中模型常挑到与本占用神毫无关系的宫干日，或把「空亡的填实之期」与「入墓的冲墓之期」
混作一谈。本层补的正是这一步：

```
yingqi：这些日子在数学上成立   →   timing：其中哪几个与本占用神有关、孰强孰弱、谁先到
```

### 四件事

1. **只留与本占用神相关的锚点**。用神与权重取自 `core/xiangyi.js`，故**随占类而变**——
   求财的应期落在生门/戊上，官司落在开门/庚上。非用神宫的同类推算记为参考级。
2. **强弱是机制与用神的关系，不是打分**。机制正好解开压在用神身上的那一害
   （空亡→填实/冲实、入墓→冲墓），纲要明言「须待…方应」，故为 `high`；
   用神宫的干日与马星动象为 `medium`；与用神无关之宫为 `low`。级别由规则库
   显式声明（`mechanism.onTarget`），不由描述字段的有无去推断。
3. **排出先后**。按同一循环内的**距今位次**（地支 12、天干 10）把并列的候选排成一条线，
   回答「先到哪个」。位次**只表先到后到，不是「几天后」**——提示词与单测都钉死这一点。
4. **定迟速**。以权重最高之用神的旺衰论：旺相应速、休囚墓绝应迟；用神入墓者纵旺相
   亦须待冲墓方发（纲要·三节应期5 + 四之二节要诀2）。

### 绝不重算干支

所有支与干**一律取自 `YingQi.analyze()` 的结果**，本层只做筛选、定强弱与排序。
若两处各推一套，模型面对两份不一致的日辰必然选错——单测逐条回查每个锚点的干支
确实出现在 yingqi 的输出中，并回归了「填实必为空亡支本身、冲实必为其六冲支、
四支类机制绝不取天干」这些实测错法。

### 零串味做到机制一级

不是整层按盘别开关，而是**逐个机制**判定：

| 机制 | 转盘 | 飞盘 | 依据 |
|---|---|---|---|
| 填实 / 冲实 | ✅ | ✅ | 两份纲要表述一致（转盘·三节应期2；飞盘·应期节同条） |
| 冲墓 | ✅ | ✅ | 转盘·三节应期4 + 四之二要诀2；飞盘·应期节「入墓」 |
| 宫干定日 | ✅ | ✅ | 转盘·三节应期1；飞盘·应期节「近期取地盘奇仪定日」 |
| 马星发动 | ✅ | ❌ | 只见于转盘·三节应期3；飞盘应期节未列此法，故不推及 |

两派通用的机制，`basis` **分别注明两份纲要的出处**（有单测强制），不是由一派推及另一派。
用神的**取用**仍是分派的：转盘用 `xiangyi` 的占类用神与权重，飞盘退回引擎自算的用神宫，
且权重如实记 0（表示「知道是用神宫，但不知其在本占中的分量」），绝不编造。

### 缺件降级

| 未传 `yingqi` | **整层停用**——本层只做筛选排序，绝不自行推算干支 |

## 案例本与校准（Phase 5 · Casebook）

### 要解决的事

前四期把「按纲要该怎么断」做成了确定性的、可溯源的证据。但**纲要说的在你身上准不准**，
应用一无所知——每次解读完，结果就丢了。本期把「预测 → 对轨现实 → 校准」这条回路补上：
案例存在手机里，事后回填实际结果，应用统计每条规则的符合率并给出校订建议。

### 最要紧的一条：经验层与教义层严格分离

**用户反馈永不改写 `knowledge/*.json`。** 这不是偷懒，是因为自动回写会一次性毁掉
前四期真正的资产：

| 若让反馈直接改规则 | 后果 |
|---|---|
| 规则被反馈改过 | `basis` 立刻变成假话——规则不再是纲要说的。可审计性与两派隔离(零串味)一并失效 |
| 各人各机权重不同 | 「同盘同占类必得同一结果」不再成立，同一张盘在两台手机上结果不同 |
| 样本量 10–50 | 一条规则命中 3 次、符合 2 次，算出的 67% 没有任何统计意义 |

所以做成两层：

```
教义层  knowledge/*.json + core/xiangyi.js   ← 只读，按纲要写，永不被反馈触碰
   │
经验层  core/casebook.js + 本机 IndexedDB     ← 记录、统计、建议
   │
   └→ CALIBRATION 条目（与 READING 分列送进提示词，明标「这不是纲要」）
```

经验层**不参与规则求值**，只给证据包附一条说明。规则层的确定性与跨设备可复现因此完好——
有单测直接钉住：灌 30 条「结果相反」的反馈后，`XiangYi.analyze()` 的输出必须逐字不变。

> Phase 6 在这两层之外加了**第三层「修订集」**：它确实参与求值，但走的是显式的、需人工采纳的
> 独立通道，且只能收窄／降权／停用既有规则。上面这条单测在 Phase 6 之后依然成立——
> 反馈本身仍然一个字也改不动规则，改动只可能来自你亲手采纳的修订。详见下节。

### 不给假精度

- 单条规则**满 8 例**才给符合率；不足则显示「样本不足 n/8」。小样本的百分比会被当成精度，
  害处大于好处。
- 生成校订建议的门槛更严（**12 例**）——建议会驱动人去改东西。
- **归因如实标注**：默认把整案对错记到当次触发的每条规则头上，这是**粗归因**（断错未必是
  某条规则错，也可能是综合时错），故每条统计都标 `整案归因`；用户逐条标注过的才标
  `逐条标注`，并优先采用。整案归因占比过高时，应用会主动提醒这一点。
- 「结果相反」单独计数——它比「没应验」更重，是断反了。

### 不生成「翻转极性」类建议

建议只有三种：`review`（复核）、`confirm`（表现稳定）、`method`（方法学提醒）。
刻意**没有**「把这条规则的助/阻反过来」——那等于让应用自创断法、越过纲要。复核建议直接
写明：若确属误收，请改 `knowledge/domain-rules.json` 并补出处，不要靠反馈去覆盖它。

### 隐私

案例里是用户问的私事（病、官司、感情）。**只存在这台设备上**，不上传、不同步、
不经过任何服务器——`core/casestore.js` 中不存在任何网络调用（有单测扫描源码禁止
`fetch`/`XMLHttpRequest`/`sendBeacon`/`WebSocket`）。要备份或换机，只有一条路：
用户自己点导出，拿到一份 JSON。导入默认**合并**，同 id 取较新者，一次误操作不会抹掉历史。

### API

```js
// 纯函数层
Casebook.makeCase({ id, now, question, domain, chart, xiangyi, timing, answer });
Casebook.applyFeedback(rec, { outcome, happenedAt, note, now, ruleVerdicts });
Casebook.calibrate(records);              // → { totals, rules[], domains[] }（含样本量门槛）
Casebook.proposals(cal);                  // → 建议数组（只建议，不执行）
Casebook.buildOverlay(accepted, cal);     // → 经验层附注
Casebook.calibrationFor(overlay, xiangyi);// → 本次触发规则对应的经验条目

// 存储层（后端可注入：浏览器 IndexedDB / 测试内存）
const store = CaseStore.create();         // store.persistent=false 表示未落盘，界面须告警
store.save(rec); store.list(); store.remove(id);
store.exportAll(now); store.importAll(data, { replace:false });
```


### 复盘：从「四个按钮」到「实况 + 反推」

四档按钮太粗，且只能支撑「整案归因」的统计。复盘面板现在收三样东西：

1. **实况文本**——用自己的话写实际发生了什么。这才是真正能拿来反推的东西。
2. **实际发生日期**——填了就触发**确定性应期反推**（见下）。
3. **逐条标注**——分两段列出，逐条标为 相符／部分／不符／相反。做了这一步，统计才从
   `整案归因` 升为 `逐条标注`。

   | 段 | 是什么 | 统计键 |
   |---|---|---|
   | **盘面象义** | 用神落在哪一宫、同宫有哪些星门神干、其传统象义。取自 `yongshen.examine`——**各盘别、各占类都有** | `sym:生门@2`（元素@宫） |
   | **规则判读** | `domain-rules.json` 命中的条目，有 `basis` 可回查纲要 | 规则 id |

   二者**分开统计、互不冒充**：规则有出处，象义只是「这盘上有这么个配置」，
   混在一张表里会让人误以为象义也有纲要依据。

   > **这里修过一个 bug**：最初标注清单只列规则判读。而综合占类的规则库近乎空白（只有一条
   > 宫际关系）、飞盘更是整层停用——于是用户看着 AI 大谈「生门临坤、白虎同宫」，回头却
   > 只有一行可标，清单名不副实。现在象义段由 `yongshen.examine` 供给，任何盘别、任何
   > 占类都不会落空。

### 应期反推是确定性的，不是猜的

引擎能算出任意日期的干支，所以「你说 5 月 12 日发生」可以直接与当时排的锚点比对：
那天是丙子日 → 命中了哪几条机制、命中在**日/月/年**哪一层（纲要·三节应期5：
近事看日时、中事看月、远事看年，故三层都比对并标明）。零猜测、零幻觉。

**同时给出随机基准**——这一条很要紧。全量锚点常有十来个候选 × 三层，蒙中概率逼近 97%，
那样的「命中」没有任何信息量。所以：

- 全量基准照实显示，并写明「候选一多几乎必中」；
- **★强锚点单列统计**——即纲要明言「须待此时方应」者（空亡→填实/冲实、入墓→冲墓），
  数量少，其命中率与基准之差才真正说明问题；
- 若强子集命中率未高于基准，界面直说「应期在你这儿暂无证据说准」。

宁可告诉你这个统计目前证明不了什么，也不给一个好看的数字。

### 复盘必须看得见当时到底断了什么

案例一直存着 AI 解读全文，但**早期版本既没显示给用户、也没喂回复盘**——人和 AI 都在
盲打分：只看到「财源有力、生机正盛」这类词条，看不到当时实际写了什么。已修：

- 复盘面板顶部折叠显示**当时的解读全文**，打分前可先对照；
- 复盘提示词带上解读原文（超长则截断并如实标注「节选前 N 字」，不让模型误以为看了全文）；
- 未记录解读的旧案例如实标注「未存解读全文」，不伪装成有。

### 断错分析（misreads）

有了原文，才谈得上「错在哪」。复盘除逐条标注外，还让模型挑出解读中**与实际明显不符的
具体论断**，每条给三样：

| 字段 | 内容 | 校验 |
|---|---|---|
| `claim` | **照抄**解读里的原句（要求不得转述——转述就无法核对） | 截断 200 字 |
| `basedOn` | 它所依据的规则 id 或象义 key | **必须是本案真实存在的条目**，编造的一律清空并报告 |
| `actual` | 实际情况如何 | 截断 200 字 |

最多 5 条。编造的 `basedOn` 会被清空但**断错内容本身保留**——那段文字仍有价值，
只是不该污染统计。

### 「被指为断错依据」是符合率之外的**另一个信号**

两者回答不同的问题：

- **符合率**答「这条准不准」；
- **被指错次数**答「解读出岔子时，是不是它在背后」。

实测能抓到符合率完全看不见的问题：某条规则符合率 100%（整案归因说「应验」），
却在 12 次复盘中被指为失误依据——此时会单独给出建议：

> **复核：这条常被指为断错的依据**　复盘中有 12 次把解读的失误归到此条，例如
> 「断言本月必进财」→ 实际：一分未进。符合率为 100%，尚可——**问题可能不在条目本身，
> 而在它被用作该论断依据的方式**。请对照纲要原文复核其适用边界。

指向象义 key 的断错不计入规则的被指错次数（二者分开统计，互不冒充）。

### AI 复盘（可选）

填好实况后可点「让 AI 依实况给出建议」：把**当时的判读条目 + 盘面象义 + 解读全文 +
实况文本**交给模型，只让它做两件事——逐条判断是否相符、指出断错之处。提示词明确禁止
新增条目、改写内容、提出新断法，并要求「实际情况没涉及的条目直接省略，宁缺勿猜」。

返回结果**严格校验后才填进表单**：编造的规则 id、非法档位一律丢弃并报告丢弃数；
观察最多 3 条且逐条截断。**AI 只是预填**，用户在界面上过目、可逐条改动，保存时记为
`manual`。模型碰不到存储，也改不了任何规则。

### 界面

解读完成后出现「存为案例」；「案例本」面板可打开复盘、查看按占类/按规则/按应期机制的
统计与校订建议，并可导出/导入。

案例本按**是否已回填结果**分两页，而不是一列到底：

| 页 | 装什么 | 为什么分开 |
|---|---|---|
| **待回填** | 还没有结果的案例 | 这是待办清单，天然短。混在几百条已结案里就找不着了 |
| **已归档** | 已回填的案例 | 这是资料库。带结果分布、四类筛选、关键词搜索 |
| **校准统计** | 按规则/象义/应期机制拆开的符合率 | 有样本门槛把关，见上文 |

两页都每次只铺 20 条，余下点「显示更多」——案例攒到几百条时，一次性 `innerHTML`

**不是准确率**：占类混杂、难度不一，拿它当命中率会高估；规则一级的符合率在校准统计页。

## AI 调用的稳定性（超时与过载）

实测反馈两类失败，根因都在客户端，已修：

### ①「自定义端点生成超时」——原实现根本没开流式

`callCustom` 的请求体里**没有 `stream: true`**，是整体生成：必须等模型把全文吐完才有第一个
字节。本应用提示词约 8K 字符、详尽解读动辄数千 token，120 秒总超时一到就整个掐断，
用户连一个字都拿不到。

修法三条：

1. **开流式**（`stream: true`），并兼容「端点忽略该参数直接回 JSON」的情形——
   那种情况下不该报错，能出结果就行。
2. **超时改为「空闲超时」**：只要还在往外吐字就不算超时；默认 90 秒**没有新内容**才中止。
   这才是流式下的正确超时姿势——旧的总时长上限会把正常但较慢的生成一并杀掉。
   另设 600 秒总时长兜底，防止服务端持续吐空白导致永不结束。
3. **中止也保留已生成内容**：断在半路时把已经写出来的部分交还，而不是全丢。

### ②「Gemini 503 high demand」——原实现只重试一次

改为**指数退避 + 抖动**重试（默认 3 次，1s → 2.2s → 4.8s，上限 15s），并**尊重服务端的
`Retry-After`**（秒数与 HTTP 日期两种格式都认）。抖动是必要的：多端同时到点重试会再次
压垮对方。

仍失败时，按用户配置的**备用链**接力：备用模型 → 备用 Provider。
**不硬编码任何备用模型名**——模型可用性会变，写死只会在日后静默失效；备用完全由用户在
设置里填，留空即不启用（有单测禁止源码中出现写死的备用模型）。

重试与切换的全过程通过 `onStatus` 显示在状态栏（「Gemini/xxx 繁忙，3 秒后第 2 次重试…」）。
干等两分钟再报错，是最劝退的体验。

### ③ 顺带修掉的 UX bug

旧的超时错误提示写着「可在设置调大 timeoutMs」——但**设置面板里根本没有这个字段**。
现已补齐：空闲超时 / 总时长上限 / 重试次数 / maxTokens / 备用模型 / 备用 Provider，
且有单测钉住「错误文案提到的设置项必须在界面上真实存在」。

### 错误分类

| 类别 | 例 | 处理 |
|---|---|---|
| 瞬时 | 429 / 500 / 502 / 503 / 504 / 断网 | 退避重试，用尽后走备用链 |
| 过载 | 503、high demand、rate limit | 同上，并额外说明「这是服务方临时过载，与你的 Key 或配置无关」 |
| 配置 | 400 / 401 / 403 / 404 / 未填 Key | **立刻报错**，不做无谓重试也不换 provider |

### 排障：先跑「连接自检」，别猜

实测报障：`gemini-flash-latest` 反复「暂时失败，5 秒后第 3 次重试…」，而
`gemini-flash-lite-latest` 与 Agnes 2.5 flash 正常。

**「暂时失败」四个字把唯一的线索吞掉了**——那是本应用自己的缺陷。从代码反推还能缩到
一个范围（`isOverloaded(e) ? '繁忙' : '暂时失败'`，故 429/503 会显示「繁忙」；
显示「暂时失败」说明是 500/502/504 或 fetch 层失败），但**具体是哪一个，用户看不到**。

现已改为**逐码明说**：

| 状态 | 文案 |
|---|---|
| 429 | 配额/频率受限(429) |
| 503 | 服务方过载(503) |
| 500 | 服务方内部错误(500) |
| 502 / 504 | 网关错误(502) / 网关超时(504) |
| fetch 失败 | 网络不通或被拦截 |
| 空闲超时 | 等待超时（未收到任何内容） |

500/502/504 的最终报错另附可操作的下一步：换 lite 版模型 / 调小「思考预算」/ 配备用模型。
单测直接断言 `reasonOf` **绝不返回「暂时失败」这类无信息量的词**。

**AI 设置里新增「🔌 连接自检」**：用当前配置发一次最小请求，把**原始 HTTP 状态码与响应体**
原样列出，且对每个环节各跑「非流式」与「流式」两次（二者行为可能不同）：

```
❌ Gemini/gemini-flash-latest（非流式）HTTP 500  {"error":{"code":500,"message":"An internal error..."}}
❌ Gemini/gemini-flash-latest（流式）  HTTP 500  {"error":{"code":500,"message":"An internal error..."}}
```

**另补上一个一直够不着的开关**：`llm.js` 早就读 `geminiThinkingBudget`，界面上却没有这个字段——
等于死配置。现已补出「思考预算」输入框（留空＝模型自定，**0＝关闭思考**）。
思考型模型遇 500 或长时间无输出时，把它设 0 往往能绕过。

### 验证

```bash
node core/llm.test.js      # 36 项：错误分类、退避、Retry-After、备用链、请求体形状、
                          #        逐码文案、connect probe 的链路×模式展开、probeRead 三家响应解析
```

浏览器内用 stub fetch 实测四种情形：500 与 503/429 文案各异且下一步不同、
400 立即报错不重试、自检两种模式各出一行原始状态码。

### 自检自己写错过一次（值得记下来）

首版自检交出的是**假情报**：四条全是 `Failed to fetch`、耗时 1–2ms，连平时能用的
自定义端点也「失败」。真因是 `buildChain` 返回的是 `{ provider, model, label }`，
而 probe 里误写成 `step.kind`——恒为 `undefined`，于是**每一路都掉进最后的 Ollama 分支**
去连 `localhost:11434`，秒失败。

1–2ms 就是线索：那点时间根本出不了浏览器。**一个会说谎的诊断工具比没有诊断工具更坏**，
所以补了单测：`buildChain` 的链路项必须带 `provider`，且断言它**从不产出 `kind`**，
probe 不得依赖一个不存在的字段。

### HTTP 200 也可能一个字都没返回

自检原先只数返回了多少**字节**，`ok` 就跟着 `r.ok` 走。这在思考型模型上会给出
反向的假情报：自检只给 16 token 的额度，思考型模型把这点额度全花在思考上，
于是返回 **HTTP 200、`finishReason=MAX_TOKENS`、正文一个字也没有**——
而自检会报「✅ 正常，返回 217 字节」。用户真正遇到的那个故障（答案空白／写一半就断），
自检恰好绕开了它。

现在自检解析响应体，报的是**正文有几个字**，并把结果分成三态：

```
⚠ Gemini/gemini-flash-latest（非流式）　HTTP 200　2ms
    连通正常，但没有返回任何正文（finishReason=MAX_TOKENS）。自检只给 16 token，
    思考型模型会把额度全用在思考上，正文一个字也剩不下——这与正式提问时
    「答案空白／写一半就断」是同一个成因：把「思考预算」设 0，或把 maxTokens 调大。
✅ Gemini/gemini-flash-latest（流式）　HTTP 200　1ms
    正常，返回正文 1 字

✅ 通且有正文　⚠ 通但没正文　❌ 没通。
```

解析走同一个纯函数 `probeRead`，三家 provider、流式与非流式共用：整体 JSON 解不动
就按行拆（SSE 的 `data:` 行 / Ollama 的 NDJSON）。Gemini 带 `thought: true` 的思考片段
**不计入正文**——把思考当正文，空答案又会看起来像正常答案，等于换个地方再骗一次。

### 截断的答案，从前和写完的答案长得一模一样

另一个实测：一次回答断在「须」字上，界面上看不出那是被截断还是模型写完了。
查下来 `sink.truncated` **只被写、从未被读**——代码注释里那句「界面会标明未写完」是假的。

现已捕获 `finishReason`（Gemini）与 `finish_reason`（OpenAI 兼容），并把结果说出来：

```
猫已随车远移，须

⚠ **本次回答未写完**（Gemini）：已写满 maxTokens 上限（当前 2048）。
请在「AI 设置 → 超时与重试」里调大 maxTokens 后重试；
若用的是思考型模型，思考也占这份额度，可一并把「思考预算」调小或设 0。
```

三种中断分别措辞：`MAX_TOKENS`/`length` → 额度用尽（附当前值）；`SAFETY`/`content_filter`
→ 安全策略中断；空闲超时/总时长 → 连接中断只取回了已生成部分。
`STOP`/`stop` 属正常写完，**一个字都不加**。

真实网络行为用本地 mock 端点 + Playwright 覆盖，六种故障情形均已实测通过：
503×2 后成功（尊重 Retry-After）、慢速流不被空闲超时误杀、端点忽略 `stream` 仍出结果、
401 不做无谓重试、备用链构造正确、**流到一半卡死时已生成内容不丢失**。

## 从反馈反推规则偏差（Phase 6 · Revise）

### 要解决的事

Phase 5 把回路补到了「统计 + 建议」为止：应用会告诉你「这条规则 12 例里只符合 4 例」，
然后就没有然后了——建议永远只是建议，规则该怎么发还是怎么发，AI 拿到的证据包一字未变。
换句话说，攒案例这件事**对下一次占断的实际影响是零**。本期把最后一段接上，做三件事：

1. **用实况修正当时那次分析**（复盘正解）
2. **用 AI 从失败反馈反推易理，改进规则偏差**（反推 → 评审 → 采纳）
3. **应验的案例进入统计，并且反过来当反证**

### 三层，不是两层

```
教义层  knowledge/*.json + core/xiangyi.js      ← 只读，按纲要写，反馈永不触碰
   │
经验层  core/casebook.js + 本机 IndexedDB        ← 记录、统计、CALIBRATION 说明
   │
修订层  core/revise.js + 本机修订集（可导出）     ← 唯一能影响求值的一层，且必须人工采纳
```

修订层是这一期唯一新增的、**能改变 `XiangYi.analyze()` 输出**的东西。所以它被三重约束箍住：

**① 只能收窄，不能新造。** 修订只有三种操作，没有第四种：

| op | 作用 | 为什么安全 |
|---|---|---|
| `narrow` | 给既有规则**追加**一个必须同时满足的条件 | 只会让规则少发，不会让它在新场景下发 |
| `reweight` | 调权，`delta` 夹在 ±2、结果夹在 1–5 | 改的是分量，不是断法 |
| `mute` | 停用该条规则 | 极端的收窄 |

模型返回 `op: 'create'` 或任何别的值一律丢弃。`narrow` 的 `when` 只认
`state / gongState / flags / with / gong` 五个键，其余键静默剥掉——**不让模型自造 DSL**。
`ruleId` 必须命中已知规则表，编造的规则 ID 直接丢弃（Playwright 实测：喂两条、丢掉一条编造的）。

**② 必须有易理，不能只有统计。** 反推提示词要求模型给出 `reasoning`——为什么在易理上
这条规则该收窄。只报「它老是不准」的候选会被拒。这条是刻意的：如果说不出理，那大概率
只是样本噪声，不是规则偏差。

**③ 应验案例是反证。** `conflictCheck()` 拿候选修订去回扫**应验**的案例：如果这条规则
在那些应验案例里也发了，那把它 mute 掉会一并毁掉那些正确判断。冲突超过 1 例，
`narrow`/`mute` 直接 `blocked` → `reject`；`reweight` 不阻断，但冲突数照报。

支撑不足 4 例的候选一律 `hold`，不给采纳。

### 每条修订自带出身

采纳后的记录长这样：

```
provenance: "本机经验修订（非《解断方法纲要》）：据 6 例不应验反推"
supportCases: [...]   conflictCases: [...]   reasoning: "…"   enabled: true
```

送进提示词时，被修订影响的判读会带上 `〔本机修订·停用/已收窄/已调权〕` 标记，
证据包顶部另有一段警告说明「本次求值应用了 N 条本机修订，它们不是纲要」。
模型因此永远知道哪几条是你的经验、哪几条是纲要——**这是 `basis` 可审计性得以保全的关键**。

修订集存在本机 IndexedDB 的 `__revisions__` 记录里，随案例一起导出，可单条停用/删除。
`indexRevisions()` 给整个集合算一个哈希（如 `9ff316b3`）写进每次求值结果，
所以「这次解读是在哪套修订下做出的」是可回溯的。

### 复盘正解

`correctionPrompt()` 把当时的证据包 + 当时的 AI 原文 + 你填的实际结果一起交给模型，
要求它判定 `verdict`：

- `derivable` —— 当时的盘**本来就能**断出实况，是分析读错了
- `partly_derivable` —— 部分能断
- `not_derivable` —— 当时的盘断不出，别硬圆

提示词里明写了两条反事后诸葛的约束：**「强行圆出一套说法比承认断不出更有害」**、
**「要给出当时就该有的读法，而不是对实际结果的复述」**。第三种判定存在本身就是防线——
一个只会说「其实早有预兆」的复盘毫无价值。

模型另外要标 `misweighted[{itemId, how, why}]`，`how` 只能是
`overrated / underrated / missed`，`itemId` 必须命中当时真实发过的规则或象义条目。

### 无修订时逐字不变

有验证钉住：不传 `revisions` 时 `XiangYi.analyze()` 的输出与 Phase 5 基线**逐字节相同**。
修订不是弥散地渗进求值，是一条显式的、开关明确的旁路。

浏览器端整条链路已用 Playwright 实测跑通：种 6 例不应验 → 反推（丢弃编造规则）→
评审 `accept`（支撑 6、冲突 0）→ 采纳 → 重新求值 **9 条判读降为 8 条，目标规则由 1 → 0**，
修订页回显正确，案例列表不混入 `__revisions__` 记录，控制台无错误。

### 运行测试

```bash
node core/revise.test.js      # 27 项：三种 op 的边界、编造规则的丢弃、易理缺失的拒收、
                              #        冲突反证、采纳记录的出身标注、修订集哈希稳定性
```

### 老实话：这一层能做什么、不能做什么

能做的是**收敛**：把一条在你这里反复不准的规则限制到它确实管用的场景里去，并且留下
为什么这么改的易理记录。不能做的是**发现**：它推不出纲要里没有的新断法，也不打算推。
样本量摆在那里——几十例的个人案例本，够用来质疑一条规则的适用范围，不够用来立一条新规矩。

## 应期的多元性：时辰 / 日 / 月 / 年（Phase 7 · Timing v5）

### 症结：算得再准，也只会说「某日」

Phase 4 把应期干支算准了、排出主次先后了，但每个锚点一律渲染成 `X日`。于是：

- 问「今天还有没有机会」——答一个日子，等于没答。事情常常就在同一天，差的只是**时辰**。
- 问「这两三个月」「今年还是明年」——还是答一个日子，远期之问永远落空。

而纲要本来就写了这几级，是实现没跟上：

| 纲要原文 | 所许单位 |
|---|---|
| 转盘·三节应期3 马星「应在寅申巳亥之**日/月**」 | 日、月 |
| 转盘·四之二节要诀2「旺相而入墓者……应期多在**冲墓之年月日时**」 | 年月日时 |
| 飞盘·应期节「**远期**：取用神宫的地盘暗干支定（**年/月/日时**）」 | 年月日时 |
| 转盘·三节应期5「**近事看日时、中事看月、远事看年**」 | 跨机制的远近规则 |

### 每个锚点在四级各读一次，但出处分两级

同一个支，在时柱读作时辰、日柱读作日、月柱读作月、年柱读作年。**位次各按各柱起算**——
四柱各支逐位递进，所以位次就是该候选下次出现的真实距离：

```
[★强] 冲墓：未　(8宫)　用神：日干、戊、值符　—— 地盘己 墓于 8宫（墓库支丑），冲开则发
    未时(13:00–15:00，第 2 个时辰后) ｜ 未日(第 3 日后 = 2024-04-13)
  ｜ 未月(六月（小暑至立秋，约 7 月上旬–8 月上旬），第 3 个月后) ｜ 未年(羊年，第 3 年后 ≈ 2027 年)
```

关键在于**不是每条锚点都能这样铺开**。单位分两级，各带各的出处：

- **〔本法原文所许〕** —— 纲要写这条法时就写明了这一级（马星「之日/月」、转盘冲墓「之年月日时」、
  飞盘远期暗干支「年/月/日时」）。可直接照断。
- **〔推及〕** —— 该法原文只写了日，这一级是由「近事看日时、中事看月、远事看年」一条推来的。
  可用，但断语里要说清是按远近推的。

**填实/冲实的 native 只有日**，因为两派纲要都再三强调「填实/冲实只能是**地支日**」。
一刀切地把每条法都推广到四级，是最省事也最不老实的做法——那样 `basis` 立刻变成假话。
有单测直接钉住这一条。

冲墓更能说明问题：**转盘四级、飞盘只日**——因为两份纲要写法本就不同，
转盘要诀2 写了「年月日时」，飞盘应期节只写「冲墓之日」。**不由转盘推及飞盘**，
`nativeUnitsBySchool` 按盘别分列。

### 补上飞盘唯一的远期专法

飞盘纲要写着「远期：取用神宫的地盘暗干支定（年/月/日时）」——这是两派纲要里
**唯一专为远期而设**的机制，此前一直没实现。盘面 `diPanAnGan` 排出的正是完整干支（如「丁卯」），
干支两半各成一锚（十日循环 vs 十二日循环，位次须各算）。仍是飞盘专有，转盘不启用。

### 先定远近，再定单位

远近本应由**所问之事**决定。用户没说时，依纲要同一句「得令旺相则应速，休囚墓绝则应迟」
以迟速作缺省推定——**并在提示词里写明这是推定，不冒充用户所述**。这一段被排在锚点**之前**：
排在后面，模型读到时早已把每一条都当成「某日」断完了。有单测钉住这个次序。

证据包另按单位各铺一行，问远问近都能直接取用：

```
若断时辰（同一日之内何时；近事必看这一级）：巳时(09:00–11:00) 即当下这个时辰；未时(13:00–15:00) 第 2 个时辰后；…
若断月（月建以节气分界，非农历朔望月）：辰月(三月（清明至立夏）) 即本月建；未月(六月（小暑至立秋）) 第 3 个月后；…
若断年（年以立春分界，所标公历年为约数）：辰年(龙年) 即本年太岁；未年(羊年) 第 3 年后 ≈ 2027 年；…
```

### 三处刻意的克制

**① 「候选何时再来」≠「事情应在那时」。** 位次折成具体公历日是历法事实，可以照用；
但事情是否应在那天，仍要结合旺衰格局判断。提示词把这两件事分开说。
（Phase 4 原本一律回避"第几天后"，那是矫枉过正——四柱各支逐位递进，位次本就是真实距离。）

**② 跨级读同一支，不是多给了一个候选。** 「午日/午月/午年」是同一个候选的三种读法。
`byUnit` 按 label 去重、只留最强来源，提示词里也明写这一条——否则模型会分别陈述，
显得处处应验。

**③ 干支称谓不能生造。** 时辰与月建以**地支**命名（午时、辰月）；天干在时/月/年三柱上
只能说「时干戊」「月干戊」「年干戊」，写成「戊时」「戊月」是生造的说法。
惟「戊日」是纲要原有用语（「用神坐丙→丙日」），照旧。

### 时辰能预测，就得能核对

复盘表单新增**可选的发生时刻**。填了才核对「时辰」一级；不填就不核对——
拿中午顶替出来的时柱去比对，等于白送一层蒙中的机会。

更要紧的是：**多评一层，随机基准必须跟着抬高**。实测同一案例，
只填日期时基准 97%，加填时刻后 99%——十来个候选乘以四层，几乎必中。
加了一层却不抬基准，命中率就被虚高了。有单测直接断言 `四层基准 > 三层基准`。

（这也再次说明：全量锚点的命中率没有信息量，真正该看的是**★强锚点**那一份——
数量少，且是纲要明言「须待此时方应」者。）

### 运行测试

```bash
node core/timing.test.js      # 51 项（新增 16 项）：四级读法齐备、位次各按各柱、
                              #   填实/冲实不得推广、冲墓按盘别分列、暗干远期两派隔离、
                              #   干支称谓、位次折算与盘日一致、byUnit 去重、远近次序
node core/evidence.test.js    # 46 项（新增 6 项）：四级读法进到证据包、远近排在锚点之前

```

## 类象用神：所问的那件东西本身也要有代表（Phase 8 · LeiXiang）

### 症结：解读永远只在四个宫里打转

用户实测反馈——「② 用神与关键宫位逐宫详析」一节，AI 翻来覆去只写**时干宫、日干宫、值符、值使**。
问题不在模型，在证据包：用神此前只按**占类**取（`domains.json`），
所问的**具体人事物**在盘上根本没有代表。

- 问钥匙——盘上没有钥匙。
- 问尸体——盘上没有尸体。
- 连问钱财，只要占类落进了「综合」，盘上也没有戊。

而转盘纲要本来就写了这一层，是实现没跟上：

> 二节用神取用表尾：「**衍象类象：人/物/事各取对应符号(见第四节)**，落宫定方位、临神临门定性质。」
>
> 二节失物一条：「玄武(盗) + **用神类象** + 年命 …… **类象定物**，方位定处。」

### 做法：从问句取象，在盘上定宫

`knowledge/leixiang.json` 把纲要**第四节的四张类象表逐字**收进来
（九星 / 八门 / 八神 / 十干，外加三节射覆的八卦类象），再给一份「所问之物 → 该取哪个符号」的索引。
解读时从问句里取象，用 `YongShen.locate` 在盘上定宫，与占类用神**并列**送进提示词：

```
· 占类用神（补充查看范围）：我方=日干；主=玄武、伤门；辅=杜门、九地
· 类象用神（所问的具体人事物本身也要取一个用神，与上面并列合参，不相取代）：
  - 玄武（失物之盗向）＝所问「丢了」，落 7宫兑·正西  〔已在占类用神之列〕〔纲要原文〕
  - 辛（金刃/首饰）＝所问「钥匙」，落 4宫巽·东南   〔本层归类〕纲要「辛(金刃/错误/首饰)」；
      钥匙、锁、刀剪皆金属小器，戒指项链即首饰，归此一类。  本象类象：金刃/错误/首饰
```

辛的**象义**与 4 宫的**方位场所之象**也一并进 SYMBOL——只给「辛＝金刃/首饰」四个字，
模型断不出它落宫是何情状，失物的「在哪里找」就还是答不出来。

### 出处仍分两级

和 Phase 7 的单位一样，不一刀切：

| 标记 | 含义 | 例 |
|---|---|---|
| **〔纲要原文〕** | 所问之词就是纲要写的那个类象词，可直接取用 | 「错误」之于 辛(金刃/**错误**/首饰)、「车」之于 伤门(伤损/捕猎/讨债/**车**) |
| **〔本层归类〕** | 是本应用把这个词归入纲要那一类 | 「钥匙」归入 辛 的「金刃/首饰」 |

`confidence` 非 high 的条目**必须写明归类理由**——归类而不说理由等于自造，有单测钉住。
表的 `basis` 也必须是**逐字**引用（如 `死门(土·凶)：死丧/停滞/坟/医`），
单测会拿它去 `assets/zhuanpan-method.md` 里对：转述久了就会与纲要漂移。

### 零串味：这是转盘专法

飞盘《鸣法·用神章》是一张按占问类型**固定取用**的表（寻物＝伤门＋年命），不含类象取用；
其射覆一条的八卦类象是**读用神落宫**之用，不是**取用神**之用。
所以类象取用只在转盘启用，飞盘一律停用并说明原因。单测直接去飞盘纲要的用神章里查：
**若那一节出现「类象」二字，这条隔离的前提就要重估**。

### 两处刻意的克制

**① 「辛为尸骨」不采纳。** 那是别家传承的说法，本仓库两份纲要皆未载。
按转盘纲要四节「死门(土·凶)：死丧/停滞/坟/医」，尸体、丧事、坟墓归**死门**。
`_notAdopted` 字段把这个决定与理由留了档——要改，先在 `assets/zhuanpan-method.md` 里有据可依。

**② 匹配不到 ≠ 盘上没有。** 索引没收的词（手机、电脑这类纲要成书时未有之物），
如实说「未匹配到」，并请模型按四节类象自行取象、写明所据——
绝不因为索引里没有就让模型略过这一步。有单测断言提示词里不得出现否定盘面的措辞。

### 顺带修掉的一个真 bug：甲定不了宫

`YongShen.locate('甲')` 一直返回 `null`——因为**甲不上天盘**（遁于旬首），三盘皆无。
从前不显眼，因为占类用神里没人直接取甲；类象一取「老板/领导/首领→甲(栋梁/首领)」，
它就永远落得「盘上未见」，等于白取。纲要既已明言「以值符落宫论」，
现在与日干为甲一路同样处理，并带 `via: 甲不上天盘，遁于旬首，以值符落宫论`——
不是新造断法，是把已有的一条补齐。

### 类象用神也进应期：问「什么时候到手」看的正是它那一宫

类象用神既然是用神，其落宫就是**用神宫**，「用神宫干支定日」「用神入墓→冲墓之日」照样适用。
从前应期只按占类象义层的 `focus` 取宫，于是「钥匙什么时候找到」算的还是玄武、伤门那几宫，
钥匙自己那一宫反而没算。现在把类象落宫并进 `yongShenGongs`（`yingqi` 只为所给之宫算宫干，
漏了它就永远算不出），锚点上标出这日子是冲谁来的：

```
[★强] 冲墓：戌 (4宫)  用神：辛〔类象·所问「钥匙」〕
    —— 天盘辛 墓于 4宫（墓库支辰），冲开则发
[★中] 用神宫干定日：辛 (4宫) 用神：辛〔类象·所问「钥匙」〕
```

这一例读来颇有意思：钥匙(辛)恰好**入墓**于巽四，正是「压着、埋着、一时不现」之象，
须待冲墓之日方出——这个断法从前根本出不来，因为钥匙那一宫压根没进应期计算。

**但不给它编造占类权重。** 占类权重出自 `domain-rules.json` 的 `roles`，类象用神不在其中，
故一律记 `0`，如实表示「知道是用神宫，但纲要没说它在本占里占多少分量」；
排序时靠机制强弱而非权重。同名同宫者（失物占里的玄武，既是占类用神又被类象取中）
只在原条目上补记类象来历，不另立一条——否则用神名单里会出现「玄武、玄武」。

### 已知边界

- 索引是**关键词匹配**，不是语义理解：问句用了同义词而索引没收，就会落到「未匹配」分支
  （此时交回模型自行取象，不会静默丢失）。想扩就往 `index` 里加，每条都要能指回纲要某个类象词。
- **六亲（父母/子女/兄弟）没有收**：纲要十干类象只写了乙(妻)、庚(夫)，没有父母子女之象。
  问「我妈的病」目前只取到天芮(病符)，母亲本人无象。要补，得先在
  `assets/zhuanpan-method.md` 里有据可依。
- 手机、电脑等纲要成书时未有之物同样不指派符号，走「未匹配」分支交回模型。

## 力量校验：把纲要早就写死、却从未执行的禁令执行起来（Phase 9 · Severity）

### 一次真实的误判

实测案例：亲属肝癌晚期，问吉凶。解读写的是「事在掌握之中」「天心旺，医疗手段有效」
「丁+戊青龙转光，病有转机」「可待寅日卯日再占」。**次日上午九点即去世。**

复盘查下来，盘上该有的凶象一个不少——时干临白虎、值使杜门+腾蛇、天芮空亡入墓、
地盘壬入墓+击刑力量仅 0.1。问题不在数据缺失，在**没人把它们对拍起来**：

```
引擎：4宫 jiXiong = 小吉
旺衰：4宫 power  = 0.08（门迫 + 天盘辛入墓）
解读：「有转机」   ← 只读了前一行
```

而纲要在四之二节把这件事写得很死，一共四条，**每一条都被违反了**：

| 纲要原文 | 出处 |
|---|---|
| 旺相之凶格，凶亦有力；**休囚之吉格，吉亦无力**。**不可只看吉凶不看旺衰。** | 转盘四之二节 / 飞盘旺衰节 |
| 同宫多害则**减力相乘**……断语须明写"因×害故力弱" | 转盘要诀1 / 飞盘要诀 |
| **衰死又入墓**者：谋事难遂，**不可强断为吉** | 转盘要诀3 / 飞盘要诀 |
| 称量力量（**必做**）：吉凶定方向，旺衰定成败大小；二者须合参，缺一不可 | 解读流程 3.5 |

**这不是缺断法，是缺执行。** `core/severity.js` 把这四条做成确定性检查。

### 五条检查，阈值从力量刻度反推

wangshuai 的力量＝天盘干旺衰基值（旺 1.0 / 相 0.8 / 休 0.5 / 囚 0.3 / 死 0.15）
× 门迫 0.5 × 空亡 0.5 × 击刑 0.5 × 入墓 0.2。阈值据此定，不是随手拍的：

- `critical = 0.10` —— 正是纲要所举「既入墓又击刑者，几近无力」之量值（1.0×0.5×0.2）
- `weak = 0.25` —— 旺干单犯入墓即 0.2，凡不足此数者必已受重折
- `strong = 0.80` —— 「相」未受折损之值，用于识别旺相之凶

| 检查 | 触发 | 禁令 |
|---|---|---|
| 吉凶与力量背离 | 引擎判吉 + 力量 ≤ weak | 不得写「有转机/可成/可控/无碍」 |
| 旺相之凶 | 引擎判凶 + 力量 ≥ strong | 不得以「虽凶但不重」淡化 |
| 多害叠加 | 四害命中 ≥ 2 | 必须逐项写明「因×害故力弱」 |
| 衰死入墓 | 天盘干囚/死 + 入墓 | **不可强断为吉** |
| 力量极弱 | 力量 ≤ critical | 以此宫为据的乐观断语一律不得下 |

只校验**关注宫**（用神宫 / 类象用神宫 / 值符 / 值使 / 日干宫 / 时干宫——纲要 3.5 点名的那几处），
不遍历全盘徒增噪音。力量与吉凶**一律取自 wangshuai 与引擎，本层只对拍、不重算**。
这一段被强制排在 FACT / READING **之前**：放在包尾，模型读到时早已按「引擎判小吉」写完了。

### 老实说：整盘那一行没有预测力

拿本机 61 例已回填案例回测整盘口径与实际结果：

| 口径 | n | 未应验/结果相反 |
|---|---|---|
| none | 16 | 31% |
| some | 26 | 38% |
| most | 19 | **21%** |

**无相关，甚至略呈反向。** 所以整盘那一行只作汇总描述，
**不推「整盘偏凶」、也不叫模型因此转为悲观**——无据的悲观和无据的乐观是同一种错误，
只是方向相反。真正有据的是**逐宫**那五条（皆纲要原文）。这个回测结论写进了
`severity-rules.json` 的 `_measured` 字段，并有单测钉住，防止日后被人当成预测器。

## 综合占类补齐：占了四成案例，却几乎不产出判读

真实案例本 72 例里，**28 例（39%）落在「综合(general)」**——而这个占类当时是
`0 条件 / 0 组合 / 1 关系`，平均每盘只产出约 1 条判读。四成的解读，规则层近乎空转。

那不是纲要没写。纲要一节「断局总纲」本就写了诸占通用的一层，只是没收进来：

> 时干宫**空亡**主事虚悬待填实；日干宫**空亡**主自身心神不定。
> 兼看两宫**旺衰、空亡、门迫**。值符值使为纲，**先看此二宫定大势**。

现补齐 19 条：日干/时干/值符/值使各自的旺衰、空亡、门迫、入墓、击刑，条条带出处。
补齐后综合类平均每盘产出 **6.5 条**判读（原为 1 条左右）。

### 顺带钉死一条实测教训：生克只断成败，不断迟速与幅度

`general.rel.日干-时干` 是全案例本触发最多的规则（24/61 例），符合率 75%，
但**被指为断错依据 6 次**——最多的一条。逐条看那 6 次：

| 断 | 实 |
|---|---|
| 延误概率极高 | 航班准点 |
| 需耐心等待抢修 | 1 小时 13 分即恢复 |
| 明日微降或持平 | 实际大幅下调 |
| 我方小胜收官 | 2:2 平局 |

**规则本身没错，是被拿去答了它不管的问题。** 纲要原文「日干宫克时干宫 → 我能制事、
谋为可成（但费些气力）」说的是**能不能成**；迟速另有其法（应期一节：得令旺相则应速），
幅度大小则看旺衰力量（3.5）。「但费些气力」这个从句被反复放大成「会延误 / 要久等 /
幅度不大 / 只是小胜」，而实况恰恰更快、更大、更顺。

故给这条关系加了 `scope: '成败倾向'` 与 `scopeNote`，并在提示词纪律里立为硬约束（E9b）。

### 另外三条纪律，也都来自真实误判

- **E9c 时干宫代表的是本次所占的那一件事。** 问句含多事时须先点明时干宫主哪一件，
  结论不得跨到另一件上——「事在掌握之中」本指通话可成，被写成了「病情在掌控之中」。
- **E9d 问病情安危不得作宽慰之辞**，也不得以「可待某日再占」代替本次该给的判断
  （那是回避，不是回答）；同时仍不得作医学诊断——**两个方向都要守住**。
- **E9a 力量校验的每一条禁令都是硬约束**，逐条照办。

## 反推跑了一遍，结论是「不该采纳修订」（Phase 10）

用户导出 72 例真实案例本，要求把够格的规则走一遍**反推 → 评审 → 采纳**。跑下来的结果，
比预想的有意思：**该改的不是那几条规则，是统计的粒度和我自己写错的两句话。**

### 先撞上的问题：六种读法被算成了一条

`general.rel.日干-时干` 在 61 例已回填案例里触发了 **28 次**，符合率 75%——看着还行。
拆开看：

| 分支 | n | 折合符合率 |
|---|---|---|
| 彼宫生我宫 | 3 | **100%** |
| 二宫五行比和 | 6 | 67% |
| 我宫生彼宫 | 3 | 67% |
| 我宫克彼宫 | 8 | 56% |
| 彼宫克我宫 | 2 | 25% |
| **二者同落一宫** | 5 | **20%** |

一条 `relation` 规则底下是**六种互斥读法**，准头天差地别，却共用一个 `id`。于是：

- **符合率是没有意义的平均数**——100% 和 20% 被抹成 75%；
- **反推做不了**——`mute` 这条会把 100% 的那一支一起杀掉。

故给关系判读加了**分支级 id**（`general.rel.日干-时干#我宫克彼宫`），校准、指错归因、
规则修订一律以它为准。`branchId` 刻意用**人读得懂的触发文本**而不是内部 kind，
因为改版之前的案例把这段文本存在 `label` 里——由它反推同一把键，**72 例既有反馈不作废**。
有单测直接灌老格式记录验证这一点。

拆分支之后，够格反推的从 6 条降到 **2 条**——另外四条本来就是把不同分支的失败凑在一起。

### 剩下的两条，反推的结论是：别改规则，改我写错的话

**① `lost_item.玄武.宫休囚死`** —— 原 concept 写作「隐匿之象力弱、**藏得不深**、较易显现」。

七例实测：**物件全都找到了**（本条的主张成立）。错的是「藏得不深」被读成「就在近处」——
而实际上包在**警察局**、房产证在**被人骑走的电动车**里、钥匙在**小区门口保安亭**。

查纲要：二节失物写的是「玄武落宫=失物/盗向；类象定物，**方位定处**」——
远近处所由**落宫方位**定，与玄武的旺衰无关；四节八神只给玄武「盗贼/欺诈/暗昧」，
**没有一个字提深浅远近**。所以「藏得不深」是我加的，纲要无据。

冲突检查也给出了同样的判决：

```
lost_item.玄武.宫休囚死  op=mute
   支撑(不应验) 5 例 ｜ 冲突(应验时也发过) 2 例 ｜ blocked=true
   → reject：该条在 2 例已应验案例中也曾触发；仅凭 5 例不应验就停用，会连带损害那些断对的情形。
```

**这不是「纲要在这儿不准」，是我抄错了。** 故改在教义层，带出处，并留 `_authoringFix` 记档。

**② `career.生门.旺相`** —— 两例断错都问「**对方会不会做**」（项目对方签不签、小伙伴来不来），
断成可成，实则未成；而问「**我方能不能得到**」（考编上岸、工作调动）则应验。

查纲要：二节事业/求职行取的是 **开门 + 值符**，生门在本占类只是辅用（它自己的 basis 就这么写的）；
而「事之向背成败」纲要一节明定由**时干宫**断。所以生门旺相只表**这件事本身有实利可图**，
不表对方必履约。同样是范围问题，不是准不准的问题。

### 于是加了 `answers`：这条只答哪一类问题

这三处（含上一期的生克关系）是同一种错——**不是规则错，是拿它去答了它不管的问题**。
故给判读加 `answers` / `answersNote` 两个字段，随判读一路带进提示词：

```
- [助] 〔只答：显隐〕玄武(失物)·7宫 宫休：隐匿之象力弱、遮蔽不住、终必显现
⚠ **断语范围**（〔只答：×〕者，其结论只落在×上，不得挪去答别的问题）：
  · 本条只断能否显现，不断远近、不断处所。远近与所在由落宫方位定，与玄武旺衰无关。
```

（字段名用 `answers` 而非 `scope`——`scope` 在证据包里另有其义：单象/组合/宫际。）

### 所以：一条修订也没采纳

跑完整条流程，最终**没有往修订集里写任何东西**。这不是流程白跑：

- 它把 6 个「问题规则」筛成 2 个（另外 4 个是统计粒度造成的假象）；
- 对剩下的 2 个，冲突检查否掉了最直觉的那个动作（mute 玄武）；
- 逐案回查之后发现，两条都是**教义层的撰写之误**，该在源头改、带出处改，
  而不是在上面糊一层本机修订。

**修订层是给「纲要说的在我这儿确实不灵」准备的，不是给「我抄错了」准备的。** 这一次是后者。

## 占类判错：最贵的一类错（Phase 11）

### 为什么 wealth 与 lost_item 规则最全、反而最不准

真实案例本里这两个占类的「完全应验」只有 11% 和 10%，是全场最低。把它们的题目列出来一看就明白了——**约一半根本不是那个占类**：

`wealth`（求财）里装着：
- 今天车发生了事故，谁的责任？人有没有事？→ 不是求财
- 网测，女士今天下午**钱包丢了**，问还能不能找到？→ **失物**
- 去国外旅游，办签证一共花了多少钱？几天下签证？→ 出行 + 数字

`lost_item`（失物）里装着：
- 对面人家新装了一道大门，该怎么办 → **风水**
- 公司要和对方谈合作，问能不能成？（"希望另**找**旅行社"）→ **事业**
- 朋友的**孩子找不到了**，已报警 → **寻人**（不是寻物）

**规则没问题，是规则被用在了不属于它的题上。** 占类一错，用神、判读、应期整套全错，事后无从补救——这是本项目里代价最高的一类错。

### 根因不是「用户选择被覆盖」

先查了一遍是不是下拉框被无视了。不是：

```
目的=综合（默认，未改） → 求财   ← 关键词自动判定接管
目的=失物（用户手动改） → 失物   ← 用户选择胜出
```

用户选了就生效。问题在于**它默认「综合」**，于是自动判定悄悄接管；而**判成了什么，用户直到答案标题栏才看得见**——那时整篇已经建在错的用神上了。

### 做法：把占类摆到提问处，实时可见、一键可改

提问框下面新增一行，随打字实时更新：

```
占类 [跟随问句自动判定 ▾]   → 本次按 求财 断  ⚠ 据问句关键词自动判定，请核对
占类 [失物 ▾]              → 本次按 失物 断（你指定的）
占类 [跟随问句自动判定 ▾]   → 本次按 失物 断（据排盘「目的」）
```

三种来源分色标明：**自己指定的**、**据排盘目的的**、**关键词猜的**。只有第三种带⚠——因为只有它可能悄悄猜错。这一处的选择优先于排盘「目的」。

### 类象层顺带升级为「占类判错」的探测器

类象取用本来就要从问句取象。取到的象若正是**别的占类**的主用神，那多半是占类判错了：

```
问句取到的象（玄武→失物）正是**别的占类**的主用神，而本次占类为「求财」，
那些占类的判读规则并未启用。**请先核对本次占类是否判对**——
占类判错则用神与规则整套皆错。
```

此前这个提示只在占类为「其他」时才出；现在**占类不符时更要出**。措辞按情形分开：占类是「其他」时说「一并合参」，占类**不符**时才说「请先核对是否判对」——不是每次都吵。有单测钉住这个区分。

### 还没解决的

- **多问一卦**：案例本里大量题目是「①②③④」四选一或三四个子问题合成一卦。整卦只给一个应验档位，结果几乎必然是「部分应验」——这解释了 36% 的部分应验率。要真解决得允许一卦拆多问、各自回填，工程量不小，暂记在此。
- 分类器本身在 `engine.bundle.js` 里，属不改之列；本期只做**可见与可改**，不动它的判定逻辑。

```bash
                             #        「其他」与「判错」措辞须分开、未传索引时不凭空猜
```

## 一卦多问：拆开各自回填（Phase 12）

### 为什么非拆不可

真实案例本 72 例里，**23 例（32%）带多问标记**。一卦问三四件事，却只给一个应验档位——
结果几乎必然是「部分应验」。这解释了那 36% 的部分应验率里相当一部分：

```
1.问钥匙能否找到？        → 找到了
2.问如能找到，在哪个地方？  → 地点没说准
整卦档位：部分应验 → 每条触发的规则都记 0.5
```

第一问明明全中，规则却只拿到 0.5 分。信息丢了，规则统计也被拖成一锅粥。

### 陷阱：选项不是子问题

硬拆会犯一个很蠢的错——

```
用什么方法治疗比较靠谱：①中医②西医③祝由道法④开刀。
```

这是**一问四选项**，不是四个子问题。拆开就成了四个「问题」，全错。

故切分器不只切，还判**这是子问题还是选项**：

| 判据 | 结论 |
|---|---|
| 过半不像问句（无「？/能否/多少/何时/什么…」） | 多半是选项 |
| 并列于同一行，且非条条成问 | 多半是选项 |
| 各自成句且多含疑问 | 多半是子问题 |

拿 72 例真数据验：23 例含多问标记 → **判为子问题 11 例（共 25 问，均 2.3 问/例）、判为选项 12 例**，
逐条核对无误。切分支持 `①②③` / `1. 1、1，` / `（一）(1)` / `一、二、` 四种写法，
并把**背景**与各问分开（「辛未命女租房，房东要卖房。问：1.…2.…3.…」的背景不会被当成第一问）。

顺带修掉切分器的一个 bug：`问：1.新房面积…` 的第 1 问会被吞掉——首段含标记但不在行首。
改成按标记位置切片后正确拆出 3 问。

### 只提议，不擅自拆

`makeCase` 存下拆分提议，但 **`confirmed` 恒为 `false`**：
不经用户在复盘表单里勾选，统计一律照旧按整卦算，行为与从前**逐字一致**（有单测钉住）。
判为选项者更是默认不勾，并在表单里挂一条警告。

复盘表单里长这样：

```
②b 一卦多问  [✓] 按 3 问分别回填     各自成句且多含疑问，多半是子问题
  1. 新房面积比旧房大还是小？   ○完全应验 ●部分 ○未应验 ○结果相反  [这一问的实况]
  2. 属于什么类型的房子？       ●完全应验 ○部分 ○未应验 ○结果相反  [...]
  3. 租金多少？                 ○完全应验 ○部分 ●未应验 ○结果相反  [...]
```

勾上并逐问打分后，「整体判断」**按各问自动推出**（全中=完全应验、全不中=未应验、
有中有不中=部分应验、全相反=结果相反），仍可手改。

### 统计上真正的差别

整案归因从「笼统的档位分」换成**各问平均分**：

| | 四问中三问应验 |
|---|---|
| 不拆（从前） | 部分应验 → **0.5** |
| 拆开逐问回填 | (1+1+1+0)/4 → **0.75** |

有单测直接对比同一批案例拆与不拆的校准结果：`0.5` vs `0.75`。

### 说清楚它没解决什么

**这修的是「结果的记分」，不是「规则的归因」。** 规则是对整张盘发的，不是对某一问发的——
拆问之后我们仍然不知道「是哪一条规则答对了第 1 问」。要那个精度，仍得靠**逐条标注**
（你已经在 57 例里做了这件事）。

拆问的价值是：把 36% 里那部分**虚高的「部分应验」**还原成真实的分数，让整卦档位和
整案归因不再系统性偏低。

```bash
                            #   只提议不擅自拆、未确认时行为逐字不变、各问平均分确实影响校准
```

## 证据合流：数「有几路互不相干的证据」（Phase 13）

### 外部评审给的诊断

一位评审看完 81 例案例本后的结论，与我自己查到的完全吻合：

> Qimen-pwa 目前有一个不错的「知识 → 证据」系统，但「证据 → 决断」的系统还很稚嫩。

他举的例子正是本项目最惨的一次失手（失落首饰）：

| 盘上有 | 最终答案写的 | 实际 |
|---|---|---|
| 玄武@离九、**九地@巽四**、**杜门@巽四** | 正南 / 明亮处 / 炉灶电器 | **卧室床下，被衣服压住** |

复盘层自己已经指出「玄武临离九 被高估、九地@4 被漏掉」。

**症结不是象义不够，是没人去数「有几路互不相干的证据指向同一结论」。**
「可能之义」被当成了「较可能之义」——离九确实可以是明亮处，但那是**一条孤证**；
而九地(稳固藏纳)+杜门(阻塞/隐藏)+玄武(暗昧) 三路都指向「藏」，反倒没被采信。

### 做法：独立路数 → 档位 → 弃权

`knowledge/dimensions.json` 把每个盘面元素对**各维度**的指向逐条列成票，每票引纲要原文：

| 维度 | 例 | 出处 |
|---|---|---|
| 方位 | 离九→正南 | 三节方位表 |
| 高低 | 坎一→低（隐伏低洼）、乾六→高（高亢楼台）、九地→低 | 三节方位表 / 四节八神 |
| 显隐 | 九地→藏、杜门→藏、玄武→藏、离九→显、景门→显、入墓→藏 | 四节八神八门 / 四之二节 |
| 场所 | 艮八→桌柜之下/坟、离九→炉灶电器 | 三节方位表 |

`core/converge.js` 据此计算：

1. **独立路数**——同一元素的多个别名只算**一路**。玄武的「盗/失物/暗昧/欺诈」是一路，不是四路。
2. **对立检出**——高⇄低、显⇄藏两边都有据时，标为相争并**各降一档**，不代为择一。
3. **档位**：A级（≥3 路）可写进结论；B级（2 路或多路相争）作次要可能须并列；
   C级（孤证或两路相争）只能标「参考」；**D级不得出现在结论里**。
4. **弃权**——某维度最好的也只到 C 级，则整个维度弃权：照实说「证据不足，不锁定」。

拿那张失手的盘跑一遍：

```
· 方位：[C级｜1 路独立证据] 正南 ← 离9宫 —— 只能标「参考」，不得写成结论
· 显隐 ⚠ 两说相争：
    [B级｜3 路独立证据] 藏（与「显」相争，已降一档） ← 杜门、九地、玄武
    [C级｜2 路独立证据] 显（与「藏」相争，已降一档） ← 离9宫、景门
· **本次须弃权的维度**：方位（仅一路孤证）；场所（仅一路孤证）；高低（仅一路孤证）
```

**「正南／明亮处」再也写不进结论了。** 这一段被强制排在 FACT / READING 之前——
放在后面，模型早已挑好一个顺眼的孤证写完了结论，再回头找理由。

### 两条边界

- **方位与场所仍以用神落宫为准**（纲要二节失物：「玄武落宫=失物/盗向……方位定处」）。
  旁宫的方位不参与定位，只把**高低/显隐**这类同维旁证计入——否则就成了拿旁宫去改方位，那是另一回事。
- **艮八在纲要同一条里既有「山坡丘陵」（高）又有「桌柜之下」（低）**，故高低两票并存、如实标注两可，
  不代为择一。有单测钉住。

### 老实说这一层能做什么、不能做什么

它**没有**让系统猜中「床下」。那张盘上「低」也只有九地一路，仍是孤证，仍要弃权。

它做的是**止损**：把一句自信的错话（「正南明亮处、炉灶电器旁」）换成一句诚实的
「方位证据不足，不锁定」。评审说得对——这是「为准确率优化」和「为答得漂亮优化」
之间最大的分野。

```bash
                            #   别名不重复计、方位以用神宫为准、不下吉凶断语、确定性
```

## 伏吟局／反吟局：补上一层从未存在过的判断（Phase 14）

### 查证：不是漏了一点，是整层没有

用户报「判断好像没有纳入反吟局和伏吟局」。查下来比预想的更彻底：

| 查什么 | 结果 |
|---|---|
| `pan.geju`（引擎格局数组） | 恒为 `[]`，从未被填充 |
| `keYing`（干加干格名）在 7 个 core 模块 | 出现 **0 次** |
| `keYing` 在 7 份 knowledge/*.json | 出现 **0 次** |
| 「反吟」二字在两份纲要之外的代码 | 不存在 |
| 象义 DSL 的条件键 | 只有 state / gongState / flags / with / gong —— **没一个能表达「格」** |

引擎其实认得干加干之格（扫 2500 盘，100 种组合里它给 81 种起了名），但那些名字只作为

写死的「伏吟…事主静滞不动、久拖难成」「反吟…主动荡、反复，速而不久」，以及应期节那句
「**伏吟主静，静中以马星为动机**」（自 v5.0.0 就一字不差抄在 `timing-rules.json` 的
`basis` 里），全都从未被执行过。

### 定义由用户给定，逐条记在案

局层面之说不见于两份纲要。**判定口径由用户于 2026-08-27 明确给出**，原样存进

> **星反吟**：天蓬星落离宫、天任落坤宫、天冲落兑宫、天辅落乾宫、天英落坎宫、天芮落艮宫、天柱落震宫、天心落巽宫
> **门反吟**：休门落离宫、生门落坤宫、伤门落兑宫、杜门落乾宫、景门落坎宫、死门落艮宫、惊门落震宫、开门落巽宫
> **伏吟局**：星、门都在原本自己的宫里

逐条核对，此表即「落于本位之对宫」（蓬坎1→离9、任艮8→坤2、冲震3→兑7、辅巽4→乾6、
英离9→坎1、芮坤2→艮8、柱兑7→震3、心乾6→巽4；门同理）。故实现按 `homes` + `opposite`
计算而非逐条硬编——等价，且不会写漏某一条。**为证明这一点，把用户那十六条逐字硬编成表，
与实现在两派各 4000 时刻共 8000 盘上对拍：不符 0 处**；单测里保留了 1000 盘规模的同一对拍。

出处分两级，逐条标注，绝不让后加的定义冒充纲要：干层〔纲要原文〕，星层、门层与局本身
〔用户所定〕并写明「出错时应回到此处重议，不可诿为纲要」。

「反吟」中「对冲」二字纲要未界定，而引擎自己命名为反吟的两格（庚+癸反吟大格、
壬+己反吟蛇刑）**并非天干相冲**，两说不合。用户裁定干层按**天干相冲**取义
（甲庚、乙辛、丙壬、丁癸；戊己居中无冲），故本层不采信引擎的反吟命名。

### v1.0.0 判漏了天芮——用户的对应表把它揪了出来

第一版有个实错：引擎在**转盘**里把天芮一律写作「禽芮」（实测 1200 盘无例外），
我把它归一为**天禽**（本位中五，恒不命中），于是**天芮从来没参与过判定**。
转盘星层因此恒少一宫——八宫只中七。更糟的是当时还把这个缺口写进注释和单测，
误释为「天禽寄芮不占宫，是数据实情，不是漏判」。

用户所列的表里明写着「天芮落艮宫」，一对照就露馅了：那两张样例盘的禽芮，一张落坤 2
（正是天芮伏吟）、一张落艮 8（正是天芮反吟），全被漏掉。

v2.0.0 改为按别名表归为**天芮**（禽寄中宫、随芮而行，判吟以芮论；天禽本身不参与判定——
用户的表只列八星）。修完转盘星层是 **8 宫中 8 宫**，与门层对齐。单测里留了三条回归守卫。

飞盘不受影响：它把天禽、天芮分写。

### 局与层分开：星门俱全才叫局

**只有星全伏、门不伏，不成局**——那只是星层之吟。达阈值（6，取自规则库）只是该
**层**成全盘；星、门两层**俱**成全盘才称伏吟局／反吟局。实测也支持这样分：转盘 3000 盘中
星伏吟与门伏吟同时发生 409 盘、只星 277、只门 260，**只有约 43% 同时**。

修好天芮后重测：

| | 转盘 | 飞盘 |
|---|---|---|
| **伏吟局**（星门俱伏） | 13.6% | 6.4% |
| **反吟局**（星门俱反） | 1.9% | 1.2% |
| 星伏吟成全盘 | 22.9%（8 宫齐动） | 10.3%（另有逐宫 43.5%） |
| 门伏吟成全盘 | 22.3%（8 宫齐动） | 10.2%（另有逐宫 43.5%） |
| 星反吟成全盘 | 11.5% | 5.4%（另有逐宫 40.8%） |

转盘是干净的全盘现象（九星按后天八卦圈整体旋转，半圈即对宫），飞盘则局与单宫兼有。
未成局者在证据包里另起一节，标「**不得以局论**，只在所命中之宫上说」。

### 转盘中宫必须排除

扫 3000 盘：**转盘中宫的天地盘干 100% 相同**（己己/丁丁/戊戊…各约 11%），这是引擎
中宫寄的结构性产物，不含信息。若不排除，**每一张转盘**都会挂一个假的「日奇伏吟」。
飞盘中宫同干率 20%，属正常分布，不排除。单测把这条写成前提断言——引擎哪天改了，该测先红。

### 应期联动：让那句抄了很久的原文真的生效

判出伏吟时，`core/timing.js` 把**马星**锚点由 medium 升为 high，并写明缘由：

```
  - [★强] 马星发动：申　(3宫)　用神：玄武
      ⤴ 本盘见伏吟，主静；纲要「伏吟主静，静中以马星为动机」，故此锚点由中升为高。
```

三条约束：只升落在用神宫的马星，只升 medium→high 不无中生有，只在转盘启用（马星取期
之法只见于转盘纲要应期节——零串味）。反吟只作「速而不久、应期宜就近且恐反复」的提示，
不改锚点强弱，因为纲要没把它写进应期节。

### 这一层不做什么

不下吉凶断语。它说的是「事动不动」，不是「事成不成」——与 severity 同一规矩。
块尾那行 `※ 本层只给倾向与出处，不下吉凶断语` 有单测锁着。也不重算盘：
星／门／干一律取自引擎 `jiuGongAnalysis`，本层只做比对。

## 八十一格：让格名带上断语（Phase 15）

### 引擎一直认得格，只是没人用

扫 20000 张盘，引擎在十干相加的 100 种组合里给 81 种起了名。但这些名字只作为一个
四字标签裸露在提示词的宫格行里：

```
5宫(中央/室内):    | 天乙/地乙(暗丁) | 小凶 日奇伏吟
```

模型看见「日奇伏吟」四个字，不知道它是什么意思。`keYing` 在 7 个 core 模块与 7 份
knowledge/*.json 里出现 **0 次**——象义 DSL 的五个条件键（state/gongState/flags/with/gong）
也没有一个能表达「格」。

### 表由用户提供，逐格录入

用户于 2026-08-27 提供《奇门遁甲 81 格局》九九表（行为地盘干、列为天盘干），
每格含格名与两句断语。全部录入 `knowledge/geju-81.json`，出处统一标
〔用户所供 81 格表〕——两份纲要只在速查表里举了十余个常见格，比这张表少得多。

**方向验证**：键写作「天盘+地盘」。录反了整层全错且不易察觉，故用四处独立佐证锁死——
戊+丙＝青龙返首、丙+戊＝飞鸟跌穴（皆见纲要 127 行原文）、戊+辛＝青龙折足与
辛+乙＝白虎猖狂（引擎实测）。单测另有一条 1000+ 处规模的全盘对拍，确认逐宫都查得到。

### 与引擎命名的 20 处分歧：并存，不合并

逐格比对：**61 格全同，20 格名称有出入，引擎无名者 0**。多数只是异体或近义
（螣/腾、反名/返名、日奇天罗/日奇入天罗）。名称实质不同者九处：

| 干加干 | 用户表 | 引擎 |
|---|---|---|
| 丁+乙 | 人遁吉格 | 玉女生奇 |
| 己+乙 | 墓神不明 | 地户逢星 |
| 庚+丁 | 亭亭之格 | 金屋藏娇 |
| 庚+戊 | 天乙伏宫 | 值符伏宫 |
| 丙+辛 | 日月相会 | 月奇相合 |
| 丙+壬 | 火入天罗 | 火入天网 |
| 庚+癸 | 移荡大格 | 反吟大格 |

「（引擎作「×」，两说并存）」。**两套说法并存而不混**，日后要重议某格有据可依。

### 两处曾经并陈的，已由用户裁定（v1.1.0）

原有两格无法凭表自决，一度并陈待决；用户于 2026-08-27 拍板：

- **癸+庚 跟随引擎**：`太户入网` → **`太白入网`**。庚为太白、癸为天网，
  「太户」二字疑为误字。
- **丁+丁 跟随纲要**：`星奇入太阴（喜事从心，万事如意）` →
  **`星奇伏吟（平至凶，事主静滞不动、久拖难成）`**。丁+丁 属同干相加，
  转盘纲要 127 行与飞盘纲要 193 行皆归伏吟类，与表上的吉义相反，从纲要。

两条都写进了 `table` 的 `name`/`text`，原表内容留在同条的 `superseded*` 字段里——
**改动可回溯**，提示词里也标「（本格经裁定，原表作「×」）」，不让改动悄悄发生。

丁+丁 这一条还带来一个出处上的后果：它的依据已不是「用户所供 81 格表」而是纲要，
故该格单独带 `provenanceOverride` 标〔纲要原文〕并指到具体行数。**出处不同就各标各的**，
不让整层的抬头替个别条目背书。单测锁住了这一点。

改完顺带做了一次全表体检：**九个同干相加无一为吉**，与纲要「同干相加＝伏吟类，
主静滞」再无相悖之处——这条也进了单测。

### 一个刚好撞上的例子

2026-01-01 00:00 之盘，1 宫丁加丁：

```
· 1宫(坎)〔六合〔类象〕〕　天盘丁 加 地盘丁 —— **星奇伏吟**
    平至凶，事主静滞不动、久拖难成　｜　该宫吉凶(引擎)：大吉
    〔纲要原文〕转盘纲要·第 127 行：「伏吟类｜…平至凶，事主静滞不动、久拖难成」…
    （本格经裁定，原表作「星奇入太阴」）
```

格名判凶、引擎判该宫**大吉**——这正是「**格之名不等于宫之吉凶**」那条硬约束存在的
理由：两说并陈，谁也不许覆盖谁。

### 两条边界

**不造吉凶等级。** 表只给名与断语，本层就只给名与断语；宫位吉凶仍以引擎 `jiXiong`
为准，二者在提示词里分列，并明写「**格之名不等于宫之吉凶**」。某宫格名凶而引擎判吉，
要照实并陈，不许拿一个去覆盖另一个。

**关注宫详列、余宫简列。** 九宫全详列会把证据包撑爆。关注宫沿用象义／类象已定的
那几宫——与力量校验同一套「哪宫要紧」的口径，免得两处各说各的。

### 顺带补上一个真空：吟局与格局都没有 E 规则

查证发现，Phase 14 的吟局虽然进了证据包、还标了「先看这一段」，但
`EVIDENCE_DISCIPLINE`（app 自己的系统提示词）里**没有一条 E 规则**要求模型使用它——
力量校验有 E9a、证据合流有 E19/E20，这两层是空的。纲要第五节的解读流程也没有这一步
（它说「采信引擎解断…格局(geju)」，而 `pan.geju` 恒为 `[]`）。

即模型看得到，却没有任何硬约束叫它必须用。现补：

- **E21**（吟局）：先据它定「事动不动」再谈成败；伏吟局不得写成「近日可成」，
  反吟局须写明其「速而不久」之性；未成局者不得以局论；
  引用时须说明该条依据是〔纲要原文〕还是〔用户所定〕。
- **E22**（八十一格）：关注宫之格名与断语须落到解读里，不得只报格名不说其义；
  格之名不等于宫之吉凶；标「两说并存」的 20 格不得只挑一个说成定论。

```bash
                          #        与引擎异名并存、不造吉凶、两处裁定与其可回溯性、
```

## 时格：五不遇时 / 天显时格（Phase 16）

### 又一层整层缺失

「五不遇」「天显」「时格」三个词在代码、7 份知识库、两份纲要里命中数**皆为 0**。

### 定义由用户给定

- **五不遇时**：时干克日干，且二者阴阳同性。义：增加凶或事难成的几率。
- **天显时格**：时干与日干相同。义：增加吉的几率，**但吉的几率不显著**。

两条判据都按定义现算，不据表查。五不遇时逐日干推出的十组——

| 日干 | 甲 | 乙 | 丙 | 丁 | 戊 | 己 | 庚 | 辛 | 壬 | 癸 |
|---|---|---|---|---|---|---|---|---|---|---|
| 时干 | 庚 | 辛 | 壬 | 癸 | 甲 | 乙 | 丙 | 丁 | 戊 | 己 |

——与传统所列（甲日庚午时、乙日辛巳时、丙日壬辰时、丁日癸卯时、戊日甲寅时、
己日乙丑时、庚日丙子时、辛日丁酉时、壬日戊申时、癸日己未时）完全吻合；时干既定，
其支由五鼠遁唯一确定，故只判干即可。单测把这十组逐一锁住。

实测发生率（4000 个时辰）：**五不遇时 10.0%、天显时格 10.0%**。两格互斥——
一干不能自克，故「时干克日干」与「时干等于日干」不可能同时成立，单测两向都验了。

两派通用：判据只是四柱，转盘飞盘共用同一份日柱时柱，不涉及任一派的排盘断法。

### 这一层刻意做得比别层「软」

用户给的口径是**「增加几率」**而非「必然如此」，天显时格更**明言「不显着」**。
这类传统说法最容易被用坏的地方，正是把一个概率倾向读成一条铁律。所以：

- **它不是禁令层**。与 severity 的硬禁令性质不同，提示词里明写这一点，
  免得模型把两类东西当成一回事。
- **天显时格定为最弱一档**（`strength: "weak"`），提示词标【分量很轻】、
  明写「不得据此加重吉断」。规则库里另记一句「『不显着』三字是用户原话，
  据此定为最弱一档，不可自行加重」——**防的是日后有人悄悄把它调重**，单测锁住。
- **效应未测，就不报**。只测了发生率，从未测过这两格与实际应验率的关系
  （案例本未按时格分层，样本也不足以分层）。故提示词里明写：不得声称
  「此类盘更准／更不准」，也不得据时格调整把握度。
- **不写解法**。传统另有「得三奇可解」之类说法，用户此次未给，**宁缺勿造**；
  E23 里还专门叮嘱模型不要自行搬用。单测断言规则库里不存在任何自造解法。

### 证据包里长这样

```
【时格】乙亥日 ／ 辛巳时　—— 出的是**几率上的倾向，不是禁令，也不是定论**。
  · **五不遇时**（时干克日干，且二者阴阳同性）：日干乙（乙亥）／时干辛（辛巳）
      义：增加凶或事难成的几率。传统谓之诸事不利、百事忌。　【倾向】
      用法：作**倾向**看，不作定论：本格只提高不成之几率，不等于此事必不成……
      〔用户所定〕两份纲要未载五不遇时。判据与其义由用户于 2026-08-27 给出……
  ※ 本仓**从未测过**时格与实际应验率的关系，故不得声称「此类盘更准／更不准」。
```

配套 **E23**：时格是倾向不是禁令；五不遇时不得据以翻成凶断；天显时格分量最轻、
不得加重吉断；不得声称此类盘更准／更不准；不得自行搬用未收录的解法。

### 运行测试

```bash
node core/shige.test.js    # 26 项：十组逐一核对、阴阳同性的反例、两格互斥（全表 + 2000 时辰实盘）、
                           #        天显最弱一档的防调重守卫、不是禁令、效应未测、未造解法、
                           #        两派通用、确定性、接入证据包
```

浏览器内实测 2026-01-01 10:00（乙亥日辛巳时，五不遇时）：时格块在 user 段位次 5099、
早于 FACT 的 5510；system 段含 E23。

## 修复：选了占类却不作数（Phase 17）

### 症状

用户在 AI 面板选「学业」，界面标签明明写着「→ 本次按 **功名** 断（你指定的）」，
整篇解读却仍按 **求财** 断——连用神都取的求财那套。

### 根因：预览与真跑走了两条不同的路

```
预览 → builder.classifyQuestion(q, fb)        认 fb，会听用户的
真跑 → builder.buildPrompt(pan, q, opts)      只认 opts.category，**不认 opts.fallbackCategory**
```

而 app 一直只传 `fallbackCategory`。实测对照：

| 传参 | buildPrompt 得到的占类 |
|---|---|
| `{fallbackCategory: '功名'}` | 求财 ← 用户的选择被静默丢弃 |
| `{category: '功名'}` | 功名 |

于是「选对占类」这件事根本做不到。而占类判错是本仓实测里**最贵的一类错**——
用神取错，整篇就建在错的地基上。修复前后用神的差别：

```
修复前（fallbackCategory:功名）→ 用神 生门@2宫、戊@1宫   「戊(财星)旺相逢生为得」
修复后（category:功名）        → 用神 景门@1宫、天辅@1宫  「文书看景门/天辅/丁奇」
```

### 修法：一个口径，两处共用

新增 `resolveCategory()`，预览与真跑都走它。口径是：AI 面板选了 → 显式；
否则排盘「目的」非「综合」→ 显式；两者皆无 → 才交给关键词。显式时传
`opts.category` 硬指定，且预览**不再过一遍分类器**——过了反而给了它推翻用户的机会，
那正是这个 bug 的来路。

### 顺带查出的第二个静默失效

`evidence.js` 里 `ev.category` 读的是 `ys.engine.category`，而 `yongshen.js` 的
`resolve()` 返回的字段名是 **`engineRule`**。误写的那行恒为 `undefined`，
于是 `ev.category` **一直是空字符串**——不报错、不变红，只是悄悄没有。已修。

## 占类三套词表：钉在一起（Phase 18）

### 分歧在哪

占类一直有三套并不同名的词表：

| | 例子 | 出处 |
|---|---|---|
| ① 界面「目的」 | 综合／事业／**财运**／婚姻／**健康**／**学业** | index.html |
| ② 引擎占类 | 综合／事业／**求财**／婚姻／**疾病**／**功名** | engine.bundle.js |
| ③ 规则占类 | general／career／wealth／**relationship**／health／lawsuit／lost_item | domains.json |

映射本身早就是数据驱动的，但**引擎对占类的支持是分盘别的，而这件事无人记录**。
实测出来：

| 界面 | 引擎占类 | 转盘 | 飞盘 | 规则占类 | 专条 |
|---|---|---|---|---|---|
| 事业 | 事业 | ✓ | **✗** | career(事业) | 有 |
| 财运 | 求财 | ✓ | ✓ | wealth(求财) | 有 |
| 婚姻 | 婚姻 | ✓ | ✓ | relationship(感情) | 有 |
| 健康 | 疾病 | ✓ | ✓ | health(健康) | 有 |
| 学业 | 功名 | ✓ | ✓ | general(其他) | — |
| 失物 | 失物 | ✓ | **✗** | lost_item(失物) | 有 |
| 官司 | 官司 | ✓ | ✓ | lawsuit(官司) | 有 |
| 出行/寻人/怀孕/风水/射覆/天气/竞赛 | 同名 | ✓ | ✓ | general(其他) | — |

**飞盘不认「事业」与「失物」**——引擎会把它们静默落回「综合」，一个专用用神都不给，
而界面照旧显示「你指定的」。这是静默降级，用户无从知道自己的选择没生效。

### 做法：把三层解析变成知识层里的一等公民

`domains.json` 新增 `engineSupport`（**实测所得**：每个占类在 4 个不同时刻各排一盘，
要求 `context.category` 相符**且** `context.yong.matched` 为真，四次全中才算支持），
并为每个不支持项写明缘由。

`YS.categoryMap(uiPurpose, school)` 一次给出全部三层：

```js
{ ui:'失物', engineCategory:'失物', engineSupported:false, degradedTo:'综合',
  degradeWhy:'飞盘纲要未列失物专用用神（玄武/伤门那套只见于转盘）…',
  ruleDomain:'lost_item', ruleLabel:'失物', hasDedicatedRules:true, loaded:true }
```

三处同时用它，任一层降级都看得见：

- **下拉框**：本盘别不支持的选项直接标成「失物（飞盘不支持）」——**选之前**就看得见。
- **预览标签**：`⚠ 飞盘不支持「失物」占类，本次会落回「综合」且取不到专用用神。`
- **证据包**：另附一句给模型——`请按综合法作答，不要凭「失物」之名硬套一套本盘并未算出的用神。`

### 两个自找的坑，都改了

**① 「有无专条」不能凭名字猜。** 我先用「`label` 是否等于引擎占类名」来判断，
结果 health 的 label 是「健康」而引擎占类叫「疾病」，二者不同名却确有专条——
被误判成「无专条」。改用 `ruleDomain !== 'general'`。

**② 数据没到位时不许给确定答案。** `categoryMap` 原先在 `DB` 为 null 时照常往下走，
于是 `engineSupported` 恒真、`ruleDomain` 恒 general、`ruleLabel` 恒空——界面煞有介事地
宣布「失物无专条」，而失物明明有。根因是知识库原先只在点 AI 时才懒加载，
而下拉标记与预览在首屏就跑了。现在：`categoryMap` 未加载时返回 `loaded:false` 且
`engineSupported/hasDedicatedRules` 皆为 `null`（不知道就是 null，不能是 true），
调用处见 `loaded===false` 即不下结论；首屏另主动拉一次知识库，加载完重算。

> 一个在数据缺席时仍给出确定答案的函数，比报错更坏——它不会被发现。

### 运行测试

```bash
node core/categorymap.test.js   # 15 项：三套词表逐项串得上（界面选项直接从 index.html 读，
                                #        免得测试里另抄一份而与界面漂移）、每个选项在 uiPurposes
                                #        里恰好出现一次、映射表无死条目、双向自洽；
                                #        **记录的引擎支持度对着活引擎逐项复核**（引擎变了先红）；
```

### 出处：逐条可辨，绝不冒充纲要

这八套**不出自纲要**，每一条 `basis` 一律以 `〔用户所定·2026-08-27〕` 起头，
与出自纲要的七套逐条可辨。单测两头都钉住：八套的 basis 必须以该标记起头、
且不得出现「纲要·」字样；原有七套则必须仍引纲要、不得被误标成用户所定。

`xiangyi.test.js` 里那条「basis 必须指向纲要或既有知识库」也随之改写——
它守的本意是**不许含糊**（不许「传统如此」「一般认为」），而不是「只能引纲要」。
现改为：必须指向一个**具名出处**，两类皆可，但不许含糊、不许张冠李戴。

### 分寸：几处刻意的克制

- **怀孕**涉母子安危：凶象照实写重，但 `_safetyNote` 明写不得作医学诊断、须建议就医；
  时干入墓／空亡一类条目 basis 里直接写死「**本条只作重警，不得单条下断**」，
  措辞里不许出现「子必死」这类话。单测逐条查。
- **天气**没有 self 角色——本占不问人事，「助/阻」在此只表该天气之象成或不成。
- **竞赛**只采一套主客口径（日干＝己、时干＝对方）。用户另给的「地盘时干 vs 天盘时干」
  一路未并行采纳，以免同一盘出现两个「己方」。
- **风水**先分阴阳宅：阳宅以值符为主气，阴宅以死门为核心，死门条明写两者判读迥异。
- 凡须另取宫/干者（年命、去方宫、坤宫定男女、物类星门…）一律写进 `_omittedNote`
  并声明**不代为指派落宫**——标「盘上未见」者按未见论。

## 股市占类：连同它自带的四条戒律一起收（Phase 20）

用户提供《奇门解盘·断股市浮沉涨跌》一文。该文除了判断纲领，**自带四条戒律**——
「一卦一事」「不能精准锁定点位」「勿以一局而赌千金之利」「术数绝非投机赌博的利器」。
这些不是附言，是纲领的一部分，故与判读**同等对待**，一并做成硬边界。

### 判断纲领落地

**主用神**：日干＝大盘或所测个股（「日干以定盘势」），时干＝股民与市场资金情绪
（「时干以观人心」）。**财星**：戊＝入市资金本金、生门＝收益、值符＝盘面主力、
景门＝消息政策。

**核心是那五条生克口诀**，全部落在 `时干 → 日干` 的一张关系表里：

| 关系 | 断 | polarity |
|---|---|---|
| 时干宫生日干宫 | 大涨 | + |
| 同宫 / 五行比和 | 上涨 | + |
| 时干宫克日干宫 | 大跌 | − |
| 日干宫生时干宫 | 下跌（价位断臂而残） | − |
| 日干宫克时干宫 | **涨跌不定**，须结合两宫旺衰综合决断 | 0 |

第五条特意判为中性并在 concept 里写死「不可单执此条」——原文说的就是「需要结合
两宫五行旺衰，综合决断」。

**取数**只分大小、不给数字：日干宫旺相取大数（定收盘点位）、休囚取小数；
时干宫定涨跌幅度，其旺衰两条**都判为中性**——幅度大不等于方向好。
`_omittedNote` 明写「不代为指派具体数字」。

时干、值符、景门三者 roleType 一律定为 `party`（本身不预设吉凶）：人气旺、主力强、
消息多，都不等于涨。

### 四条戒律怎么送达

写进 `safetyNote`，随占类进证据包，前置于判读：

```
· ⚠ 本占类边界：本占的戒律出自原文，与判读同等要紧，不可略去：
① **一卦一事**：一局只测大盘，或只测单一支股票。「不可一局之中，同时研判多只个股…」
② **不锁定点位**：「…并不是一张稳赚不赔的藏宝图。」
③ **不作投资建议、不承诺获利**：「勿以一局，而赌千金之利…绝非投机赌博的利器。」
④ 伏吟局主震荡磨底、久盘不动；反吟局主暴涨暴跌，极易追高被套。
```

配套 **E24** 进系统提示词，把它们变成硬约束：不得同局测多只、不得报具体点位或
精确涨跌幅、不得出现「建议买入/卖出/加仓/满仓」一类操作指令、不得承诺收益；
第④条与【伏吟／反吟】段联读。

### 顺带修好一个静默失效

写这一套时才发现：`_safetyNote`、`_focusNote`、`_boundaryNote` 这些**带下划线的字段
从不送达**——生效的字段名是 `safetyNote`（无下划线，health 用的就是它）。
也就是说 Phase 19 给怀孕写的那段安全边界，**从落地起就没到过模型手上**。
已改名修好，并在 `domains8.test.js` 里加了断言：不得只留在带下划线的字段里。

### 一个我自己埋了又填的坑

「股市」与「财运」都映到引擎的「求财」（引擎不认股市，会落回综合、无用神；
而求财的生门/戊恰是本纲领的两个财星）。但规则占类原先是**从引擎占类反推**的，
于是 `normalizeDomain('求财')` 按插入序先命中 wealth，股市专条永远跑不到。

改法分两步，两步我都先写错过一次：
① `categoryMap` 改为**优先按界面选项**解析规则占类；app 显式选择时用
`catMap.ruleDomain` 而非从引擎占类反推。
② 但第一版里我给 `categoryMap` 传的是**已转换过的引擎占类**（求财），
于是又绕回 wealth——必须传界面选项原值（股市）。故 `resolveCategory()` 增出

## 取数：宫数这一路此前根本不在候选里（Phase 21）

### 起因是一次断错，但错的不是算术

一张高考分数盘：AI 断 560～580，实际 **620**。事后复盘时 AI 自陈——
「按现有纲要规则与盘面信息，无法合理解释并推导出超常发挥考了 620 分」。
那句自陈是对的，也是**允许且重要的答案**：强行圆出一套说法，比承认断不出更有害。

但它没说到点子上。问题不在推理，在**数源只有一路**：

| | 此前 | 现在 |
|---|---|---|
| 天/地盘干河图数 | ✅ 有（`core/yingqi.js` 算、TIMING 段送达） | ✅ |
| 用神落宫的**后天宫数**（洛书数） | ❌ 不是候选 | ✅ |
| 用神落宫的**先天卦数** | ❌ 两份纲要皆无 | ✅ |

纲要「范围大则**乘宫数**/层数」一句里，宫数只当**倍率**使，从来不是一个可取之数。
用户的读法是：丁奇落乾六取 **6**、时干庚落坤二取 **2**，连读得 62、定量级得 **620**。
这条路此前走不通——不是走错了，是没有这条路。

### 五条纲要、四条用户所定，一条都不许混

| 出处 | 内容 |
|---|---|
| 〔纲要原文〕 | 河图数表；单取；两干相加；旺相足数/休囚减半或取个位；范围大则乘宫数·层数 |
| 〔用户所定·2026-09-03〕 | 后天宫数**作独立候选**；先天卦数（乾一兑二离三震四巽五坎六艮七坤八，中五无卦）；**连读**；**定量级** |

先天卦数按后天宫号索引：`{6:1, 7:2, 9:3, 3:4, 4:5, 1:6, 8:7, 2:8}`，中五宫返回 `null`
而非 0 或 5——它本就没有先天卦数。

「旺相足数、休囚减半或取个位」这一句纲要**只对河图数说过**，故**宫数一律出足数**，
并在提示词里把这一点写明：要给宫数打折，那是你的取舍，不是纲要的。

### 本层最要紧的一件事，是报出「可达几个数」

数源一多，事后总凑得出实际值。那不是断准，是拟合。
所以本层强制报出 **reachable（本盘可达的相异数值个数）**：

```
· 【取数】数源逐用神列全。**宫数一路（后天洛书数／先天卦数）是新补的**——
  · 丁 落 6宫(乾·西北)·宫相·力量约0.8：天盘丁河图=2、地盘壬河图=1、后天宫数=6〔用户所定〕、先天卦数=1〔用户所定〕
  · 时干 落 2宫(坤·西南)·宫旺·力量约1：天盘庚河图=9、地盘庚河图=9、后天宫数=2〔用户所定〕、先天卦数=8〔用户所定〕
  · **本盘可达 19 个相异数值**（0～96）：0、1、2、3、4、5、6、8、9、10、12、18、26、29、45、62、69、92、96。
    定量级的移位尚未计入——移位一开，这批数在每个量级各来一遍。
  · 给出数之后须说明：在这 19 个候选里凭什么选中它。
    理由若只是「它最接近某个已知值」，那不是断，是拟合——此时应当直说此盘取数无据。
```

用户那个 620 是**已经知道答案之后**凑出来的，属事后复盘。三个用神就有 19 个可达值，
连读的**次序**还是自由的（62 与 26 都在候选里），量级也是自由的——所以它不构成
对连读法的验证，规则库里原样记下这一点（`compose[concat]._userCase`）。

配套 **E25／E26**：取数前须先声明四件事（取哪个用神／哪个数源／哪种组合法／哪个量级、
量级依据是问题里的哪句话），写在数**之前**；给数之后须说明凭什么在 N 个候选里选中它；
**数字题允许弃权**——用神休囚入墓或候选过多而无从取舍时，答「取数无据」是正当的。

### 实机验证时揪出的一个自造的错：减半论干不论宫

初版拿**宫**的旺衰去裁「旺相足数、休囚减半」。浏览器里一眼看出不对——证据包写着
「日干 落 4宫·**宫死**·力量约1：天盘庚河图=9**(减半4)**」：宫死而干旺，力量还是 1，
减了个寂寞。纲要那一句紧接河图数而言，旺相的主语是**那个干**——数是干的数，
旺衰自然论干；宫与干本就可以一衰一旺，拿宫去裁干的数，减对了也是碰巧。

改为天地两干**各判各的**（`sources.hetuTian.adjust` / `hetuDi.adjust` 各自独立），
宫的旺衰仍照常显示作背景，但不再当裁量依据。现在同一行读作
「天盘庚**旺**河图=9、地盘丁**囚**河图=2(减半1／个位2)」——一旺一囚，各归各。

### 顺带修好的两处，也出自同一次复盘

**① 虚克**：当时断语说「4 宫克 5 宫，直接压制分数突破空间、封死上限」，
而 4 宫力量只有 **0.03**（夏木休囚 + 天地盘壬皆入墓皆击刑）。宫际关系此前
**只判五行、不问施方有没有那个力气**——力量 0.03 的宫去克，与力量 1.0 的宫去克，
读出来分量一模一样。现在施方力量 ≤0.25 者标【力薄】、≤0.1 者标【虚】：

```
- [阻] 天辅→日干·4宫→5宫 彼宫克我宫：… （依据：…）
  ⚠ 施方4宫力量仅 0.03（天盘壬入墓、地盘壬入墓、天盘壬击刑），此路作 **虚**（施方力量≤0.1，
  纲要谓之几近无力）读：… 〔出处：〔用户所定·2026-09-03·据纲要§旺衰推〕〕
```

阈值与 `severity-rules.json` **同源同值**（0.1／0.25），两处不许各定一套。
出处标〔用户所定·据纲要§旺衰推〕——纲要原文只说了「**该宫自身**的吉凶随旺衰增减」
（「旺相之凶格凶亦有力；休囚之吉格吉亦无力」「既入墓又击刑者几近无力」），
推到「它对**他宫**的生克亦随之折减」是补的一步，不冒充原文。
**E27** 同时堵住反向滥用：施方无力只说明**这一路**阻力不重，不是把凶断翻成吉断的许可。

**② 天辅去向**：当时只把天辅当分数的助阻读，漏了它对**学校性质与方位**的对应。
实际考上师范（天辅主文教，象中了），方位则在震三而天辅在巽四（**邻宫，没中**）。
新增 `study.天辅.去向`（`polarity: "0"`，只答去向不答分数），三条硬边界写进 `answersNote`：
①休囚入墓击刑只减「得力与否」，不改去向所指；②方位断**正位，邻宫不算命中**——
那一例就是断错了，不得事后说「东南也算东边」把它圆成命中；③性质与方位分开陈述、分开认账。
`when.gong` 列八宫不列中五（中宫无方位可断，写进触发条件而非只写在叮嘱里）；
材料出处另立 `_ingredients` 一栏——「天辅＝文教」「巽＝东南」确实出自纲要，
但据此断去向是用户所定，两层分开写，不让 `basis` 读起来像有纲要背书。

### 未测的仍然未测

宫数入候选能不能让数字题更准、虚克折减能不能提高准头——**本仓一个数据都没有**。
补它们是因为原先缺一个数源、缺一个折减，不是因为测出来更准。这句话写在提示词里
（每次都出）、写在规则库里（`_effectNotMeasured`、`_notMeasured`）、也钉在测试里。
案例本已按本层分层记录 `qushu.reachable` 与用神落宫，攒够带回填结果的数字题
才第一次谈得上评估。

## 界面：四害上盘、目的下岗（Phase 22）

### 门迫、击刑、入墓，此前在九宫格里一个字都没有

它们只出现在下方「九宫详解」的文字里、以及喂给模型的证据包里。看盘的人从格子上
根本看不出来——而纲要把这四样并称四害、明令「断成败必须称量，不可略过」。
盘上不显，等于每次都要低头去别处对。

现在标在盘上，但**刻意不动五行色**：格子里的门/星/干本来就按五行着色
（木绿·火红·土褐·金橙·水蓝），再拿颜色改字会把五行读乱。故一律另加
**角标 + 该字的描边**，字色照旧归五行：

| 标记 | 含义 | 落在哪里 |
|---|---|---|
| <sub>迫</sub> 暗红 | 门迫（门克宫，力减半） | 那个**门**上 |
| <sub>刑</sub> 橙红 | 击刑（六仪落其刑宫，力减半） | 那个**干**上 |
| <sub>墓</sub> 深紫 | 入墓（仅余两成，须待冲墓） | 那个**干**上 |
| 空（黄圈）+ 整格斜纹 | 空亡（吉凶皆减半，须填实/冲实） | 整宫 |
| 马（绿圈） | 驿马 | 整宫 |

入墓与击刑是**某个干**的事，故天盘干、地盘干各标各的，不是整宫挂一个牌子——
证据包那边早先就吃过这个亏：门/星的墓刑其实是「所落之宫内有干墓刑」，混作一谈就失真。
判定一律取自 `core/wangshuai.js` 的 `isRuMu`/`isJiXing`，门迫取引擎的
`jiuGongAnalysis.menPo`，界面**不另抄一份表**；WangShuai 缺席时一律不标——宁可不标，不可乱标。

一个字既入墓又击刑（纲要谓之「几近无力」）时，两害合成**一个**角标「墓刑」、描边取内外两圈。
初版让每害各出一个角标，实机截图上「壬墓刑」直接冲出格子——右列只有约 34px 宽，
字身已占 18px，两个角标必然溢出。改为合成一个、且**绝对定位贴在字的正上方**，
横向零占位，实测九宫无一处溢出。四害两派通用（飞盘纲要亦有「四害」一节），转盘飞盘同标。

### 排盘栏的「目的」撤了

自 Phase 17 起它对解读**已不起作用**：真正决定取用与判读的是 AI 面板的「占类」
（走 `opts.category` 那一路），而「目的」只进 `calculate()`。两个下拉并存、语义又不一样，
正是实测里误导过人的地方。

- 选项表整个搬进占类下拉（从前是启动时从「目的」搬过来的，那个下拉一撤就搬空了）
- 排盘的 `purpose` 改向占类下拉要值（`purposeNow()`），留「自动判定」时按综合排，与从前默认一致
- `resolveCategory()` 只认一个来源，`source` 从三档收敛为 `ai`／`auto` 两档
- **改占类会连带重画「分析与建议」**——用神是按目的取的，从前得回头再按一次「排盘」才更新，
  等于把这件事推给了用户。重画只另排一张同时刻的盘取其分析结果，`window._pan` 一动不动：
  整盘重排会作废「存为案例」的素材，而那份素材与占类无关，不该因为改了个下拉就丢

### 测试第一次跑就抓到一处疏漏

`core/panmarks.test.js` 是源码守卫（界面没有可单测的纯函数）。其中一条钉 `sw.js`
的 `CACHE` 名——改了界面不换缓存名，已装过 PWA 的用户看到的还是旧版。本次正是漏了这一步，
第一次跑就红了。这条钉的是**当前**名字而非「变了就行」：变没变机器判不出，
钉死之后下次改界面的人必然要来动这一行，也就必然会想起换缓存这回事。

```bash
node core/panmarks.test.js  # 20 项：三害角标与提示语齐备、判定取自 WangShuai 不另抄表、
                            #        缺 WangShuai 时不乱标、转盘飞盘各自接线、
                            #        诸害合成一个角标且墓居首、四害样式不动五行色、
                            #        三色互不相同也不与五行色重合、角标绝对定位不占宽、
                            #        inPurpose 已从 html 与 app 绝迹、占类下拉自带 17 项、
                            #        两条排盘路径共用 purposeNow、改占类重画但不动 _pan、
                            #        CACHE 名已更新
```

全套 **806 项**通过。浏览器实测（转盘/飞盘/山向三种盘、DPR 3）：
四害标记数与 `WangShuai.analyze` 逐宫相符，九宫无一处横向溢出，图例在位，
改占类后「分析与建议」跟着换用神而 `window._pan` 不变，控制台无错误。

## 基准线：把整本跑成一张成绩单（Phase A）

改进若不能被测量，就只是换个说法而已。`core/evaluate.js` 把一份案例本导出跑成
**可重复、可比对**的报告——既是现状的体检，也是此后一切改动的基准。

```bash
node core/evaluate.js 你的案例本导出.json          # 文本报告
node core/evaluate.js 你的案例本导出.json --json   # 结构化，便于两次比对
```

App 里也有：「校准统计」页顶部的 **📊 生成评估报告**。

### 当前基准（72 例 / 61 回填）

```
■ 覆盖率
  已回填 84.7%　存了解读全文 100%　做了逐条标注 93.4%
  填了实际日期 24.6%　填了实际时刻 3.3%　有断错分析 68.9%

■ 结果分布（n=61）
  完全应验 32.8%（20）　部分应验 36.1%（22）　未应验/相反 31.1%（19，其中相反 8）
  加权分 0.508

■ 按占类
  general(n=28)     完全应验 42.9%　未应验/相反 32.1%　加权 0.554
  lost_item(n=10)   完全应验 10%　　未应验/相反 30%　　加权 0.4
  wealth(n=9)       完全应验 11.1%　未应验/相反 33.3%　加权 0.389
  career/health/relationship/lawsuit  样本不足，不给率

■ 规则可靠度（分支级）
  条目 177 条，达 8 例门槛者 **1 条**
  样本分布  n=1: 87　n=2-3: 67　n=4-7: 22　n≥8: 1

■ 应期（n=15）
  ★强锚点 58%　随机基准 53%      ← 仅高于基准 5 个点
  全量基准 97%（十来个候选×多层，几乎必中，故只看★强子集）

■ 断错与未支撑断言
  断错分析 124 条，平均每例 2.03 条；**挂不上证据者 31（25%）**

■ 可核验性
  实况文本中位 16 字；**不足 20 字者 35 例（57.4%）**
```

三个数字值得单独拎出来：

- **规则可靠度只有 1 条够格。** 177 个分支级条目里 87% 样本数 <4。这就是为什么我不做
  `effectiveWeight = baseWeight × reliability`——用 n=1~3 估出的可靠度去乘权重，是放大噪声。
- **★强锚点 58% vs 随机基准 53%。** 应期这条线目前**几乎没有证据说它准**。
- **57% 的实况不足 20 字。** 那类反馈够判「大体中没中」，撑不起核验方位、应期、数量这类具体断言。
  想提高可测性，先从写长一点的实况开始。

### 最要紧的设计：只报能算的

评估器**拒绝**给出算不了的指标，并把每一项连同缘由印在报告末尾：

| 算不了的 | 为什么 |
|---|---|
| 逐条断言准确率 | 案例本只记了**断错**的断言，未记全部断言——**分母不存在**。硬凑一个数比不报更有害 |
| 方位/处所属性准确率 | 预测侧没有结构化存下「断的是哪个方位」，只有自由文本 |
| 时辰级应期准确率 | 仅 3.3%（2/61）填了实际时刻，样本不足以成率 |
| 置信度校准曲线 | 此前未存过置信度——**本版起开始存**，见下 |
| 改动前后的因果效应 | 本报告是横截面，不是对照实验。要归因某次改动，须比对改动前后各自积累的案例 |

单测直接钉住这一节必须存在、条条有缘由，且「逐条断言准确率」的缘由必须点明
**分母不存在**——不许含糊带过。

### 让「算不了」的清单随时间缩短

本版起，案例会存下**证据合流的档位**（哪个维度断了什么、几级、几路、是否弃权），
复盘表单也新增了**逐维度标注**。两者齐备后，评估器就能算**档位校准**：

```
■ 档位校准（说是 A 级的，后来对了几成）
  A级：82%（11 例）
  B级：61%（14 例）
  C级：样本不足 5/8
```

档位若名副其实，A 应明显高于 B、B 高于 C。**若不然，档位就是摆设**——
这是检验证据合流层是否真有用的唯一办法。弃权的维度不计入（本就没给结论，无从算准不准）。
